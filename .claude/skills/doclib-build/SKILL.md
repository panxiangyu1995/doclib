# doclib-build · 项目蒸馏为文档图书馆

## 使命

把一个真实项目蒸馏成一座纯 Markdown 的文档图书馆，使其成为"足够完整的规格书 + 架构蓝图 + 实施指南"。验收标准只有一条：**陌生的 agent 只读图书馆、不看源码，能在别处从零开发出功能 ≥90% 复原的项目。**

## 何时使用

- 项目里已运行 `doclib init`，且 `doclib plan` 生成了 BUILD 任务书（位于 `.doclib/tasks/`）
- 已有图书馆残缺/严重过时，需要系统性重建

## 工作流

1. **读任务书**：打开 `.doclib/tasks/` 下最新 BUILD 任务书，其中含 CLI 采集的项目清单（语言/框架/规模/入口/顶层结构）
2. **三遍扫描源项目**（这是唯一需要通读源码的阶段，之后一切以文档为准）：
   - 第一遍·骨架：清单文件、入口、路由/页面/命令清单、目录职责、依赖图
   - 第二遍·数据：数据模型/Schema/存储格式/接口契约/配置项全集
   - 第三遍·行为：逐功能梳理触发方式、正常路径、边界、错误、并发/幂等/性能约束
3. **填充图书馆**：按骨架逐卷撰写。顺序：00-overview → 10-architecture → 20-modules → 30-features → 40-guides → 90-reference → 最后更新 INDEX.md
4. **自检**：执行下方"覆盖度清单"，全过才算完成
5. **收尾**：运行 `doclib verify`，然后 `doclib snapshot --note "initial build"` 固化基线

## 反克隆铁律

- 禁止成段搬运源码。文档承载的是**行为、契约、设计意图、验收标准**，不是字节
- 允许 ≤10 行的示意片段用于澄清歧义（精确的报错文案、正则、协议样例等）
- 写"它保证什么"，不写"第几行干了什么"

## 各卷写作要点

- **00-overview/feature-map.md 是全馆之锚**：必须穷尽所有用户可感知行为（页面/接口/CLI 命令/后台任务/定时任务/配置开关），每项标注对应文档。复原者按它验收
- **10-architecture**：技术选型必须带理由与约束（为什么是它、不是什么替代品）；数据模型给到字段级；关键决策写 ADR（决策/背景/被否备选/后果）
- **20-modules**：每卷讲清职责边界、对外契约（输入/输出/错误）、内部关键流程；frontmatter 的 `covers` 指向该模块的代码目录或文件
- **30-features**：每个功能一份行为规格，含**可执行的验收标准**（Given/When/Then）。这是 90% 复原度的量化基础，宁可多不可漏
- **40-guides/rebuild-plan.md**：复原的施工顺序——按依赖关系分阶段（脚手架 → 数据层 → 核心域 → 接口层 → 次要功能 → 打磨），每阶段给出依据文档与完成标准
- 所有文档的 `covers` 必须填写真实代码路径（文件或目录），它是日后增量更新的锚点

- [ ] INDEX.md 收录全部文档且每条摘要准确
- [ ] 所有文档 frontmatter 的 covers 指向真实存在的路径
- [ ] rebuild-plan.md 的阶段覆盖全部模块与功能，依赖顺序成立
