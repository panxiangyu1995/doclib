# doclib-rebuild · 从零复原

## 使命

只凭 doclib/ 图书馆（规格书 + 蓝图 + 实施指南），在目标目录从零开发出功能 ≥90% 复原的项目。

## 硬约束

- **信息隔离**：只允许读取 doclib/ 图书馆（及其 REBUILD 任务书）。禁止访问源项目目录、源码、git 历史
- **从零开发**：所有代码在目标目录新写。文档中的 ≤10 行示意片段是行为规格，不是拿来抄的代码
- **忠实于文档**：技术选型、模块边界、数据模型、行为细节以文档为准

## 工作流

1. **通读**：doclib/README.md → INDEX.md → 00-overview → 10-architecture → 40-guides/rebuild-plan.md
2. **制定施工计划**：依 rebuild-plan 的阶段划分，写入目标目录 REBUILD-LOG.md（阶段、依据文档、完成标准）
3. **逐阶段开发**：脚手架 → 数据层 → 核心域 → 接口层 → 次要功能 → 打磨。每阶段完成即对照依据文档自检，并在 REBUILD-LOG.md 记录结果。每阶段收口的测试链与阻塞纪律遵循 doclib-dev skill 情形 B（馆内 test-chain 为准；受阻即停，禁止假装完成）
4. **验收**：逐条执行 30-features 的验收标准（Given/When/Then），记录通过/偏差；feature-map 全绿才算完成
5. **收尾**：在 REBUILD-LOG.md 输出差异清单——文档未覆盖而自行决策的部分、与文档不符被迫偏离的部分。这份清单将反哺图书馆的下一轮更新（回到源项目执行 doclib plan → doclib-update）

## 回灌沉淀规则（PRD F3 v0.32）

回灌建议与副本校准**必须改写为正式章节内容**，禁止补丁式粘贴：

- 差异知识落到对应卷的正规段落（如"必填参数表"直接写成 90-reference 的契约规格、"形状未定义"直接补进 30-features 行为规格），不留"S2-05/回灌补记"式引用壳
- **馆内正文禁止出现工作痕迹字样**：实验编号（S\d-\d+、D-\d+ 等）、答卷日期、"实测补/暂记复原口径/回灌补记/原仓库答卷"——这些属过程材料，留在 REBUILD-LOG/答卷/差异清单原处；`doclib check` 注记污染检查会拦截
- 校准副本同样按文体学规范（PRD §7.6）改写：narrative 卷保持教科书结构，ledger 册条目走五要素

## 歧义处理

- 文档明确 → 照做
- 文档沉默 → 按架构卷的选型与 40-guides/conventions 的惯例做最自然的实现，记入差异清单
- 文档自相矛盾 → 优先级：30-features（行为规格）＞ 20-modules（结构描述）＞ 10-architecture（总览）＞ 00-overview（愿景），并记入差异清单
- 文档缺失关键信息无法继续 → 停下，在 REBUILD-LOG.md 记录阻塞点，请用户回到源项目补文档，而不是凭空捏造

## 三阶段施工语义【P1→P2→P3 串行】

- **P1 信息零遗漏**：馆内记载的一切信息 100% 复现（面/端点/页面/资产形态/语义），差异清单只允许"馆未覆盖且自行决策"项
- **P2 质量保证**：行为语义与馆内契约完全一致（形状/参数/边界/错误面），门禁全绿（typecheck/lint/test/build）——测试链以馆内 `50-testing/testing.md` frontmatter `test-chain` 声明为准（doclib-dev 情形 B）
- **P3 升华超越**：在 P2 基础上产出**升华提案清单**——修复你发现的馆内/源设计缺陷、体验改进、文档增强；逐条记录（改了什么/为什么优于原状），回传主持方评估（部分改进可反哺源项目）
  - 升华挖掘加速器（可选）：源项目已建知识图谱时，`doclib graph draft` 的 unused.md（死代码候选）与 `doclib graph explore` 影响面半径可作提案素材——候选仅线索非结论，采纳前必须核实动态调用误报

## 目标感

90% 是设计值：缺的 10% 通常是纯实现细节（代码风格、内部小函数、历史 quirk）。但功能、行为、数据、接口、部署方式必须完整复原——这正是 30-features 验收标准存在的意义。三阶段之上，复原的终点是**超越**：升华提案让重建物比原仓库更完善。
