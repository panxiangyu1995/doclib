# DocLib PRD — 可复原的文档图书馆

> 状态: **活文档**。本 PRD 是产品唯一事实源，随需求澄清持续更新。
> 现有 v0.1 代码为**参考原型**：与 PRD 冲突时以 PRD 为准，PRD 稳定后再回调实现。
> 标记约定：【已确认】= 用户明确拍板；【提案】= 设计者给出、待用户确认。

## 为什么

把任意项目蒸馏成一座**可复原的文档图书馆**——文档不是开发后的负担而是开发的输入：agent 只凭图书馆即可从零重建项目（≥90%），且文档随代码持续保活。背景、痛点与产品定位见 §1、§2。

## 是什么

一套"纯 Markdown 图书馆（12 卷基线 + 实体登记簿）+ CLI 保活执法（13 命令）+ agent skills（10 册方法论）"的系统化规格与验收系统。术语与结构见 §4、§7，命令与 skills 见 F6、F7。

## 怎么运转

三条工作流闭环：build 蒸馏建馆 → update 实时保活（三层：实时同步/双锚点/diff 兜底）→ rebuild 隔离复原（基准校准）；check/verify/audit 提供从机器门禁到语义抽查的质量分层。各功能需求详见 §6（F1–F16）。

## 1. 背景与问题

1. 一个项目的完整知识（功能、结构、架构、设计意图、边界行为）散落在代码与开发者脑中，新环境/新人/新 agent 无法凭代码快速获得全貌
2. 直接克隆代码不可取：要的是**从零重新开发**的能力——文档承载意图与设计，而非字节
3. 传统文档是一次性产物：代码持续演进，文档迅速腐烂，没有人维护
4. 新项目与半成品项目同样缺少系统化的规格与验收载体——开发意图只存在于聊天记录与开发者脑中，agent 无法据此持续、可验收地开发
5. **文档资产失序无治理**【v0.17】：知识文档散落各处（README、docs/、各类规划/spec 目录、对话导出）互不衔接、无单一事实源；序号型资产（数据库迁移、接口版本等）编号无权威、易乱易重；开发过程知识（规划、规格、踩坑）干完即散，不回流沉淀——即使采用了 SDD 类工具，spec 完成即冻结，治理问题依旧

## 2. 产品定位

**北极星原则【已确认，v0.10】**：图书馆必须是**活的、可用的、利于项目开发的**——绝不是死的文档。

- **活**：三层保活（实时层 / 流程层 / 兜底层）保证图书馆与代码互相映证、永远新鲜；快照链可追溯
- **可用**：agent 无需人工交代即可自助使用（引导文件 + skills）；能直接依据图书馆开发与验收；知识广而全
- **利于开发**：图书馆不是开发后的产物，而是**开发的输入**——每次开发从图书馆出发、以图书馆验收

> 运行准则：一切后续设计决策以此为准绳——凡是让图书馆变死的方案（一次性生成、无人消费、纯事后补账）一律否决。

**核心定位**：DocLib 是一套**系统化的项目规格与验收系统**——纯 Markdown 文档图书馆是项目的唯一事实源，agent 依据图书馆完成开发与验收。

**一句话**：把任意项目蒸馏成一座**可复原的文档图书馆**：有索引、有层次、覆盖全；任何 agent 或人只凭这套文档即可在别处**从零重建**该项目（≥90% 功能复原）；且文档随项目演进**持续保活**。

**查询顺序理念【v0.18 拍板】**：图书馆是 agent 查阅项目信息的**首选渠道**——**先查图书馆，再查代码**：实体问题（某 API 的字段与响应结构？某图标用在哪？）应从登记簿直达，而非死命 grep 代码；登记簿条目带实体级 covers 指针，agent 查代码后可回馆**验证**，查码所得**回填建账**——查询即飞轮，图书馆越查越准。图书馆即 **Markdown 形式、实时更新的代码库知识图谱**：节点是实体条目，边是 covers 锚点与条目间交叉引用。

**复刻的意义【已确认】**：复刻存量项目不是最终目的，而是图书馆设计完备度的**校准标尺**——只有当图书馆能达到高保真复原，才证明其结构足以驱动任何开发。此后同一套架子用于：从零开发新项目、接手开发到一半的项目继续开发与迭代。即：**复刻是验证手段，文档驱动开发是最终目的**。

**复原即基准测试【v0.19 拍板，方法论体系见 F14】**：复刻的校准作用系统化为**多项目基准实验**——给多个现有开源项目建馆，隔离复原，对比原仓库与复原仓库的差异，差异即图书馆缺陷的显影：对症下药完善后回归重试。完备度无法自证（写的人不知漏了什么），只有复原者能显形缺口；多项目的**共性缺陷**即为基线结构与 schema 演进的实证依据（裁决 Q15/Q25/Q26）。

## 5. 目标与非目标

**目标**

1. 蒸馏：任意代码项目 → 完整文档图书馆（见 F1）
2. 复原：图书馆 → 从零重建项目，功能复原 ≥90%（见 F3）
3. 保活：代码任何变更后文档可增量跟进，无论落后一个还是十个版本、甚至从未建过（见 F2）
4. 双受众：人能轻易读懂，agent 能精确解析与执行
5. Agent 自助：任何通用 agent 进入项目即可理解 DocLib 的使用方式（见 F5）
6. 文档驱动开发：新项目从图书馆出发开发，半成品项目补建图书馆后继续开发与迭代（见 F8）
7. 一键进入：npx 安装到任意 repo，按目标 agent 适配安装 skills 与引导文件（见 F10）

**非目标**

1. **不是克隆**：不搬运源码（≤10 行示意片段除外），不追求字节级一致；缺失的 ~10% 是设计值（代码风格、内部小函数、历史 quirk 天然不被文档承载）
2. 不替代版本管理（git）：DocLib 管"代码 ↔ 文档"同步，不管代码版本历史
3. 不绑定特定 agent 产品：skills 为通用格式，CLI 为独立进程
4. **不做多环境真实漂移检测【v0.21】**：dev/staging/prod 实际 schema/配置比对是运行时问题——DocLib 只保证环境矩阵**文档**存在且保鲜（70-deploy），不承诺检测真实环境，防止范围蔓延

## 6. 功能需求

### F1 蒸馏 build（P0）【已确认目标，细节部分为提案】

输入：任意完整项目。输出：文档图书馆。

- 覆盖内容：功能、特征、结构、架构、数据流、依赖、设计决策、边界行为等**所有相关内容**
- 图书馆结构：有索引、有层次、覆盖全（结构规格见 §7）
- 生成方式：agent（按 doclib-build skill 的方法论）撰写；CLI 负责项目清单采集（语言/框架/入口/结构树）并生成 BUILD 任务书
- 反克隆铁律（写入 skill）：文档只写行为、契约、设计意图、验收标准
- **冷启动文档资产盘点【v0.17】**：对从未使用 DocLib 的 repo（存在文档不全/落后/散落等失序问题），init/BUILD 除项目清单外同步扫描**馆外文档资产**（README、docs/、各规划载体、散落 spec 等），产出收编清单；每份资产三态处置——**收编**（内容入对应卷）/ **豁免**（ack 登记理由）/ **废弃**（过期即清）；收编后 README 瘦身为**入口页 + 独立摘要**（快速开始/结构总览保留，详细知识指向馆，Q21）；常见规划载体（`.plan/`、`.specify/`、`openspec/` 等）检测后**建议声明**（检测只是建议，声明权在用户）；已声明规划载体的过程材料不收编、不进图书馆（双轨制，见 F9）
- **登记簿建账【v0.18】**：BUILD 含实体层建账——CLI 确定性扫描产出实体清单（路由定义、图标引用等模式化目标）作为**候选**，agent 逐项确认/补全/撰写五要素条目；机器只出候选不代写，撰写与裁决权在 agent（§7 细粒度保活三角）；登记簿族按分期推进（API 先行）
- **归位决策树写入 skill【v0.20】**：BUILD/UPDATE 落任何文档一律走 §7.5 归位决策树定位唯一归宿，落位即登记两级索引（INDEX + 所在卷 _index）
- **写作方法论【v0.32】**：叙述文档一律按 §7.6 文体学撰写——教科书五段（导读/为什么/是什么/怎么运转/怎么验收/参考）、叙述与表格配比（倾倒即缺陷）、粒度启发式（一篇书一个主题；正文 <10 行卡片化回炉；>300 行考虑拆分）；skill 落地为"写作方法论"章节，门禁见 F4

### F2 保活 update（P0）【已确认目标，细节部分为提案】

触发：项目发生任何二次开发/新开发之后。

- 冷启动：图书馆不存在 → 走 F1 全量蒸馏
- 热更新：图书馆存在且落后 N 个版本 → CLI 计算"当前代码 vs 最新基线"的漂移，映射出受影响文档，生成 UPDATE 任务书；agent 按最小扰动原则增量更新
- 版本间距无关性：落后的 N 个版本在最近一次 snapshot 时被一次吸收，流程不因 N 变大而复杂化
- **init 即 snapshot【v0.17】**：init 完成后立即引导首次 snapshot 固化基线——零起点 repo 从第一时间起只有增量漂移语义，不存在"落后 N 个版本"的烂账滚雪球；与版本间距无关性共同保证"无论从多乱的状态接入，治理起点永远干净"

**三态更新与默认不删除【v0.18 拍板】**：更新图书馆**不仅是新增内容**——旧内容必须同步治理，按性质三态分流：

1. **失真**（当初就写错了）→ 直接修正，保留即毒药
2. **过时**（曾经对，现在变了）→ **降级不删除**：登记簿条目走状态机（`deprecated`/`removed`，记录何时/为何/被何取代）；叙述段落移 `99-archive/` 并原地留**墓碑**注记；决策类内容（ADR）永不删除，被推翻时标 Superseded 指向新决策——"旧决策为什么错"与"新决策为什么对"同等重要
3. **冗余**（重复表述）→ 合并去重，合并处留交叉引用

- **物理删除仅限三类**：纯失真、临时产物、用户显式指令；其余一律降级保史
- 技术兜底：更新动作经快照链留痕，误删可从最近基线追回
- **落位即登记【v0.20】**：新文档落位时同步登记 INDEX 与所在卷 _index（§7.5 三级索引体系），索引滞后由 check/verify 兜底

**移除规程【v0.22】**：功能移除不是普通编辑，而是**全馆联动的治理事件**——残留问题（移除不彻底的死代码/死路由/死配置）的根源是把移除当作"删代码"而非"注销资产"。六步规程（写入 doclib-update skill 与实时同步映射表）：

| 步 | 动作 | 机制依托 |
| --- | --- | --- |
| 1. 影响面预查 | 查登记簿**反向引用**（条目 ID/名称反查依赖方）→ 受影响面清单 | 登记簿交叉引用 |
| 2. 残留扫描 | 机器扫描代码引用（路由/调用点/配置键/依赖声明）→ 残留候选 | F15 扫描器（agent grep 起步，ast-grep 增强） |
| 3. 执行移除 | 代码、路由、配置、依赖逐层清理 | 常规开发 |
| 4. 馆内联动 | feature-map → retired；登记簿条目 → removed（时间线：何时/为何/由谁）；叙述文档墓碑；必要时 99-archive | 三态更新 |
| 5. 执法闭环 | 跑 `doclib check`——removed 条目 + 代码残留引用 = 可疑引用警告，残留未清即违规 | F13 实体级对账 |
| 6. 留痕 | progress.md 补记移除事件 | 进度账 F11 |

与三态更新的关系：三态管"内容过时"，本规程管"实体消亡"，互补不重叠。

**实时同步原则【已确认，v0.9】**：12 卷基线**一视同仁**——开发中凡有改动触及任一卷的知识（测试发现 bug 与解决办法 → 95-lessons；lint/配置变更 → 60-config；部署变更 → 70-deploy；UI 变更 → 80-design……），agent 须**实时更新入馆**，不等事后 diff。此规则必须写入 CLAUDE.md / AGENTS.md 约束 agent（见 F5）。

保活分三层：

1. **实时层（主）**：开发中即时更新，由引导文件中的实时同步规则约束 agent
2. **流程层**：F9 双锚点——`.plan/` 规划工作流内的登记与归档
3. **兜底层**：`diff` → `plan` → UPDATE 任务书，捕获一切遗漏的漂移，保证最终一致

### F3 复原 rebuild（P0）【已确认目标，细节部分为提案】

输入：图书馆（+ REBUILD 任务书）。输出：全新目录中从零开发的项目。

- 信息隔离：复原者只允许读图书馆，禁止访问源项目
- 施工顺序：按图书馆内复原路线图分阶段推进
- 验收【已确认：纯 agent 自检】：agent 逐条执行图书馆内功能规格的可执行验收标准（Given/When/Then），过程与结果留痕于 REBUILD-LOG.md；功能总清单全绿 = 复原完成（90% 达成）。用户可随时抽查，但不作为流程必需环节
- **同题共答【v0.19】**：基准实验中（F14），同一套验收标准在原仓库与复原仓库双跑，逐条对比行为结果——验收不是自说自话，而是与原仓库同题共答；差异按缺陷四分类处置

### F8 文档驱动开发（P0）【已确认 v0.3；BOOTSTRAP/RESUME 任务书已实现 v0.25】

图书馆不仅用于复原存量项目，更是**一切开发与迭代的规格与验收基准**——任何项目（全新/半成品/成熟）都可以通过系统化图书馆进行接下来的开发。

| 模式 | 起点 | 图书馆角色 |
| --- | --- | --- |
| distill（存量） | 已有完整代码 | 由代码蒸馏而来；复原能力校准其完备度（见 F1/F3） |
| bootstrap（新项目）【提案命名】 | 想法/需求，尚无代码【已确认输入：对话式挖掘】 | agent 通过对话挖掘需求，直接把图书馆填实（无需用户预写需求文档）；功能以 planned 状态入 feature-map；agent 按图书馆开发并逐条验收 |
| resume（半成品）【提案命名】 | 开发到一半的项目【已确认规划来源：用户为主 + agent 建议】 | 已有代码蒸馏为 implemented 条目；未来功能规划由用户提供为主、agent 分析后可给建议供筛选，整理为 planned 条目；此后按图书馆继续开发迭代 |

设计推论（提案）：

- feature-map 状态机：`planned / in-progress / implemented / retired`——功能从规划到落地的全生命周期在图书馆中可见；保活循环同步维护该状态（进度账设计见 F11）
- 验收体系一等公民：30-features 的验收标准既是复原验收基准，也是日常开发验收基准
- 三种模式共用同一图书馆结构、同一保活循环、同一任务书机制，仅任务书类型不同（BUILD / BOOTSTRAP / RESUME / UPDATE / REBUILD）

### F11 进度账与对账兜底（P0）【已确认，v0.11】

**问题**：图书馆完整 ≠ 知道进度走到哪——开发到一半时，agent/开发者不知道进度对应图书馆哪些内容；且开发者可能忘记走 `.plan/` 流程，兜底不能依赖"每次都记得"。

**进度账（双层）**【已确认 Q16】：

- **状态事实源**：`00-overview/feature-map.md` 的状态字段（planned / in-progress / implemented / retired）——每条功能的精确进度，全馆唯一事实源
- **时间线视图**：`00-overview/progress.md`——按时间记录每次开发：日期、关联 `.plan` 文档、完成的 feature-map 条目、状态变化、涉及卷；快速回答"开发完成了哪些"
- 纪律：状态只认 feature-map，时间线只叙述不另立状态，避免两本账打架；progress.md 每条记录引用 feature-map 条目与 `.plan` 路径

**三层兜底（全部不依赖 .plan 存在）**【已确认 Q17：三层全上】：

1. **规则兜底**：引导文件（F5）写死会话纪律——会话开始跑 `doclib status`（看漂移与待办）；会话结束前自检：改动是否归档、feature-map 状态是否推进、progress.md 是否补记
2. **对账兜底**：CLI 对账报告——对比"代码漂移"与"进度账"：漂移路径无任何 planned/in-progress 条目对应 → 报"未登记的开发"；implemented 条目的 covers 失效 → 报"进度与代码不符"；任何 doclib 命令均可携带该对账输出
3. **重建兜底（终极）**：`doclib reconcile` 命令——即使 `.plan/` 全部遗漏、进度账彻底失真，基于快照链 + covers 映射 + 漂移自动生成"疑似已完成开发清单"，agent 逐项确认后补录 feature-map 与 progress.md。**进度永不真正丢失：代码 hash 与 covers 映射本身就是底层账本**

**reconcile 已实现【v0.25】**：`doclib reconcile` 产出三段对账报告（疑似完成/进度不符/待推进），agent 按 doclib-reconcile skill 逐项确认补录。后置（路线图）：git hook / CI 集成对账，漂移未同步时在提交或流水线阶段警告。

### F9 规划载体适配与知识回流（P0）【v0.17 重构：载体兼容制；声明+提醒已实现 v0.25】

**设计原则【v0.17 拍板】**：DocLib **不输出工作流，只回收知识**——开发者用什么规划载体（`.plan/`、spec-kit 的 specs、OpenSpec 的 changes、任意自定义目录）是开发者的自由，DocLib 一律兼容，不强逼开发者改变既有习惯；只负责让载体中的规划/规格知识按双锚点回流图书馆。

- **载体声明**：init 时声明规划载体路径（可多个，默认 `.plan/`），记录于 state；载体内部格式 DocLib 不解析、不约束、不收编；后续可改声明，改后提示重新扫描（Q24）
- **用户既有工作流【已确认】**：以 `.plan/<今日日期>/` 为默认实例——规划内容包含：想达到的目的与效果、问题点、研究结果、代码实际情况、设计的方案、有无备选方案、具体的实施清单等。**DocLib 不提供规划文档模板**【已确认 Q11】，完全保留用户的规划习惯；spec-kit/OpenSpec 用户同理保留其 spec/change 习惯

**双锚点机制**【已确认 Q9；v0.17 解耦：绑定载体而非特定目录】：

| 锚点 | 触发 | agent 动作 |
| --- | --- | --- |
| 锚点一 · 登记规划 | 载体中规划/规格文档完成后 | 将规划登记进图书馆：feature-map 新增 planned 条目（或更新既有条目）；受影响的架构/模块文档可加规划标注 |
| 锚点二 · 归档成果 | 该规划的开发完成后 | 双轨沉淀【已确认 Q12】：① 过程材料留在原载体不动（.plan 用户不丢 .plan，spec-kit 用户不丢 spec）；② 长期价值内容（决策、研究结果、备选方案理由）沉淀进图书馆（ADR/规格/参考卷）；③ 更新受影响的正式文档与 covers；④ feature-map 状态推进 planned → implemented |

**双轨边界【v0.17 明确；v0.35 增设唯一白名案例外】**：已声明载体的过程材料**永不进图书馆、不做收编**（豁免于孤儿检测，见 F13）——只有知识沉淀后才入馆；载体是过程资产，图书馆是事实源，二者互不侵扰。**唯一例外【v0.35，ADR #19】**：agent 对话原始记录（transcript）作为「可复原性档案」入馆分区 `98-sessions/`——会话记录在部分工具侧默认 30 天自动清理（不导出即真丢），且对话是比规划文档更原始的决策过程证据，与复原基准 P1「信息零遗漏」同向；例外仅限对话导出，其余过程材料边界不变。

**提醒刚度【v0.17；v0.36 分层】**：CLI 检测所有已声明载体，在 `status` / `plan` 输出中持续给出"待登记 / 待归档"提醒——载体中存在未登记的规划文档、或已实现但未归档的条目时逐次提醒，**直至清零**（mtime 型提醒保持 soft，Q23 原拍板；存在性子集的 strict 执法见归档闭环强验证【v0.36】）。载体目录加入快照忽略，不进代码快照、不进图书馆【Q10 延续；对话原始记录档案区为白名案例外，见双轨边界【v0.35】——其位于馆内 `98-sessions/`，doclib/ 本就不入代码快照，边界自洽】。**载体检测建议【v0.36，兑现 F1】**：init/status 检测常见规划载体（`.specify/`、`openspec/`、`specs/`、`.kiro/specs/`）存在且未声明且含 .md → 软提示声明（声明权在用户）；`place list` 对载体形态文件首建议声明而非收编。

- 源项目引导文件：按 F5 轻量片段声明知识回流规则（双锚点 + 提醒语义），使 agent 在日常开发中被规则约束——规则表述对任意载体成立，不以 `.plan/` 为唯一措辞

## 7. 文档图书馆结构【双层结构：叙述层 12 卷基线（v0.8 定稿）+ 实体登记簿层与档案卷（v0.18）】

设计原则【已确认】：图书馆之义在**广而全**——凡项目涉及的知识类别皆应入馆。下列为**基线分类法**：agent 按 skill 依项目实际增补卷（编号顺延，如安全、国际化、性能、合规…），宁多勿缺；反之不适用的卷可标记不适用并说明理由，不得静默省略。

**双层结构【v0.18 拍板】**：

- **叙述层（12 卷基线）**：讲**理解**——行为、契约、设计意图、验收标准；"为什么、怎么运转"在这里
- **实体层（登记簿族）**：供**查询**——逐实体条目，机器可 grep、状态可对账；"某个 API 长什么样、某图标用在哪"直达登记簿；条目带实体级 covers 与交叉引用，构成知识图谱（理念见 §2）
- 两层互引：叙述文档引用登记簿条目，登记簿条目回指所属模块/功能——查事实去登记簿，查理解去叙述
- **细粒度保活三角**（细粒度不死于此）：实体级 covers 锚点 + CLI 确定性扫描出"实体漂移候选"（agent 撰写裁决，机器不代写——区别于 DeepWiki 死文档路线）+ 实时同步规则（实体变更当场入账）
- **开放册制【v0.21；v0.23 落点定稿 Q25：分散挂靠各卷】**：登记簿按"册"组织——**册即资产类型**，条目五要素、状态机、ID 规则、实体级 covers **框架通用**，新资产类型 = 新册，不新增范式；**挂靠表**：`api`/`error-codes`/`events-def`/`integrations` → 90-reference、`ui-assets`/`routes` → 80-design、`config`/`flags` → 60-config、`tasks` → 70-deploy、`events` → 00-overview（新类型按就近语义挂靠）；建册准入三标准：① 可枚举（清单型资产）② 有状态机意义（会废弃/漂移/该死没死）③ 变更有影响面（多方依赖）；扩展册排期由 F14 基准实验实证驱动（哪类资产反复被查询/对账失败即为下批册依据）；schema 形态见 Q26、分界判据见 Q29
- **分层职责【Q29 复用性判据】**：被多文档引用的事实 → 登记簿（单一出处）；一次性叙述中的细节 → 叙述层；两层冲突时**以登记簿为准**（登记簿是事实源，叙述引用它）
- **分期【v0.18】**：API 登记簿先行（确定性最高）→ routes/config → UI 资产（图标引用扫描最杂，殿后）；扩展册见下方候选清单（Q35）

```
doclib/
├── README.md               # 入口：怎么读、维护铁律
├── INDEX.md                # 总索引：全部文档 + 一句话摘要（登记簿各族目收录）
├── 00-overview/            # 项目定位、术语表、功能总清单（状态事实源）、progress.md 进度时间线
├── 10-architecture/        # 架构总览、数据模型、数据流、依赖选型与理由、ADR
├── 20-modules/             # 每模块一卷：职责、边界、契约
├── 30-features/            # 每功能一份行为规格 + 可执行验收标准
├── 40-guides/              # 复原/开发路线图、编码约定、开发工作流
├── 50-testing/             # 测试方案、测试矩阵、测试设置、运行方式
├── 60-config/              # 工程设置全集：lint/format、构建、CI/CD、环境变量、配置项
├── 70-deploy/              # 部署：环境矩阵、发布流程、基础设施、运维与回滚
├── 80-design/              # UI/UX：design.md、设计系统、交互细节、资产说明
├── 90-reference/           # API/接口/协议精确参考
├── 95-lessons/             # 经验教训：bug 与解决办法、代码审查沉淀、踩坑记录
├── [实体登记簿层]           # 开放册制（分散挂靠各卷，Q25）：api/error-codes/
│                           # events-def/integrations→90-reference、ui-assets/routes→
│                           # 80-design、config/flags→60-config、tasks→70-deploy、
│                           # events→00-overview；条目五要素框架通用
└── 99-archive/             # 档案卷：过时叙述与退役文档 + 墓碑元数据（不参与覆盖度考核）
```

各卷要点：

- **50-testing**：测试方案（策略/分层/覆盖目标）、测试矩阵（功能 × 环境 × 输入组合）、测试设置（框架/fixture/测试数据）与运行方式；bug 修复后的回归用例回填此处
- **60-config**：一切设置的"是什么、为什么、怎么改"——lint/format 规则及理由、构建管线、CI/CD、环境变量全集（名称/用途/默认值/是否必填）
- **70-deploy**：部署形态、环境矩阵、发布流程、回滚预案、基础设施依赖
- **80-design**：UI/UX 设计文档（design.md）、设计系统（颜色/字体/间距/组件规范）、关键交互细节、视觉资产位置
- **95-lessons**：与 F9 双轨沉淀对接——bug 与解决办法、代码审查结论、踩坑与规避；只记可迁移的经验，不记流水账；测试发现 bug 后**实时入档**（实时同步原则，见 F2）
- **实时性**：各卷一视同仁——开发中凡触及任一卷知识的改动，实时更新入馆，不待事后 diff（见 F2 实时同步原则）
- **10-architecture/dependencies**：依赖选型升级为决策记录——选了什么、为什么、考虑过的替代品、升级与替换策略
- **10-architecture/migrations**：数据库迁移治理账本（F12）——命名规则、唯一取号、applied 不可变、forward-only、登记表
- **完备性判定升级**（提案）：verify 除文件覆盖率外，新增"知识类别完备性检查"——对照基线分类法与增补清单，报告缺失/未判定的知识类别
- **登记簿册制要点【v0.18 立族；v0.21 开放册制】**：
  - **首批册**：**api**（覆盖所有前后端 API——路径/方法、请求字段、响应结构、错误码；废弃与未使用**绝不静默**）、**ui-assets**（前端资产逐项登记——图标名称、使用位置清单、状态、数量）、**routes**（前端路由表/页面结构）、**config**（配置项全集）、**events**（项目级重大变更事件账——时间 × 为什么改 × 影响了什么功能 × 关联 feature-map 条目）
  - **扩展册候选【Q35：第一批认可为"允许清单"】**：第一批（认可，建册按准入三标准触发）——`error-codes`（错误码/消息登记）、`flags`（特性开关账本，含清理机制）、`tasks`（定时任务清单）、`integrations`（第三方集成：服务/回调/限额/凭证位置）、`events-def`（MQ topic/webhook 事件定义）；第二批（F14 实证后定）——`permissions`（权限矩阵）、`enums`（枚举/常量）、`dict`（数据字典）、`i18n`（文案 key）、`tokens`（设计 token）
  - **不建册**：fixture（入 50-testing 叙述）、环境矩阵（入 70-deploy 叙述）——状态机价值低
  - **版本化条目【v0.21】**：多版本并存（如 API v1/v2）由条目标识承载（标识含版本号），各版本条目独立走状态机——v1 deprecated 与 v2 active 并行可见，消除多版本混乱
  - **条目五要素（Q26 格式定稿：frontmatter + 自由条目）**：**标识/covers/状态机进 frontmatter YAML**（机器锚点，grep 结构化通道）；**契约细节/时间线用正文**（可读通道）——五要素俱全方为合格条目
- **99-archive 档案卷要点【v0.18】**：只进不出的沉没层——收容过时叙述段落与退役文档；每份带墓碑（失效时间/原因/取代者指针/原路径）；INDEX 标注"档案区"；不参与覆盖度考核与保鲜要求；归档动作经 update 流程、快照链留痕（误删可从最近基线追回）

- 纯 Markdown 层级【已确认】：目录编号即层次，INDEX 即索引，frontmatter（YAML）为 Markdown 生态惯例，承载 covers 等机器锚点

## 7.5 归位宪法与骨架编号规范【v0.20，用户拍板】

**归位宪法**：任意 repo 启用 DocLib 后，**所有文档在 doclib 中都有正确的地方可去**——馆内是默认，馆外是例外，例外必须显式。

**归位决策树**（agent 落任何一份新文档前必须走完，写入 skills 与引导文件）：

```
这份文档是什么？
├─ 项目知识（行为/架构/决策/经验/规格）→ 12 卷对应卷
├─ 实体事实（API/图标/路由/配置）→ 实体登记簿族
├─ 过时内容 → 登记簿状态机降级 / 99-archive（留墓碑）
├─ 过程材料（规划/spec/草稿）→ 规划载体（F9，开发者自留，不进馆）
├─ 机器状态（快照/任务书/ack 账）→ .doclib/ 簿记（不进馆）
├─ 给 agent 的指令 → 根目录引导文件（技术约束例外）
└─ 项目门面（README/LICENSE/CHANGELOG）→ 根目录（生态惯例例外）
```

**馆外白名单（封闭枚举）**——馆外放文档仅限两类：

1. **技术约束类**：CLAUDE.md / AGENTS.md（agent 目录约定）、根 README / LICENSE / CHANGELOG / CONTRIBUTING 及其**多语言变体**（`README.<locale>.md` 等，生态惯例，位置由生态决定不可迁移）、.github/ 工作流模板
2. **用户显式类**：开发者明确要求馆外 → 必须 `doclib ack --standing` 登记理由；无登记的馆外知识文档即孤儿

**白名单第 1 类扩围【v0.29】**（实证依据：context7 官方规范 + GitHub 全网路径检索 + 43 仓库全量文件树；研究留痕见 `.plan/2026-10-22/orphan-placement-pack.md`）——原枚举仅 4 个目录前缀，43 仓样本实测：旧实现共判孤儿 36,086（其中**工具链类误报 2,052**，均值 ≈48/仓、AI 工具仓最高 171 in cline/gemini-cli/codex）；扩围后工具链类误报清零，真知识目录判定 23,920 保持不变（差额 3 为嵌套引导文件 docs/CLAUDE.md 等，按「引导文件任意层级豁免」正确排除，非漏报）。扩围后三类豁免：

| 豁免类 | 范围 | 语义 | 是否进代码账 |
| --- | --- | --- | --- |
| 工具链目录 | `.claude/ .agents/ .opencode/ .cursor/ .github/ .gemini/ .codex/ .cline/ .clinerules/ .roo/ .continue/ .qwen/ .windsurf/ .kiro/ .factory/ .trae/ .junie/ .kilocode/ .antigravity/ .specstory/ .crush/ .codeium/ .mcp/ .archon/ .conductor/ .greptile/`（目录前缀匹配）+ `.windsurfrules .cursorrules .roorules .clinerules .augment-guidelines`（整文件名精确匹配） | 位置由工具链决定，不可迁移 | **是**（工具链占位的技术资产仍需漂移感知） |

**非文档资产另立一面【v0.29】**：`vendor/ third_party/ deps/ extern/ external/ .changeset/` 等第三方与工具产物**不参与文档扫描**（不进代码账、不判孤儿）——与"豁免"是两回事：豁免=不判孤儿但仍跟踪，非文档资产=根本不进文档视野。`docs/` `design/` 等真知识目录**不整体豁免**（逐份判定，Q20 不变）。

孤儿 = **归位宪法违反记录**（F13 执法语义）：每份孤儿必须沿决策树归位，或进白名单、或 ack 登记——不允许"先放了再说"。

**骨架与编号规划**（万级文档的可导航性保证）：

| 层级 | 组织单元 | 规则 |
| --- | --- | --- |
| 馆级 | 两位编号卷 00–95（99-archive 预留） | 可扩展卷顺延编号，卷数不膨胀 |
| 卷级 | 卷内文档 / 二级分区 | **卷内文档强制三位序号前缀【Q33】**（如 `010-user-auth.md`，机器排序稳定）；分区/分册阈值 30 篇【Q33】→ 超限按业务域分子目录（如 `30-features/cli/`），分区必带 _index.md；**目录层次硬上限 3 层**（馆/卷/分区），防深洞；**存量文档不强制追溯**（最小扰动），新增文档一律强制 |
| 册级 | 登记簿条目分册（如 api-core.md） | 分册阈值 30 篇触发，每册带 _index.md |
| 条目级 | 实体条目 + 条目 ID【Q34 前缀命名空间】 | ID = 类型前缀 + 递增（`API-001`、`ICON-014`；前缀清单 API/ICON/ROUTE/CFG/EVT/ERR/FLAG/TASK/INTG…随册扩展），**前缀即命名空间保证跨册唯一**；版本化条目格式 `API-001@v2`；ID 是交叉引用、对账报告、时间线的唯一锚；**retired 条目的 ID 永久退役，不复用不回收**（防引用悬空，序号权威原则同源） |

**三级索引体系**：`INDEX.md`（馆级）→ 各卷 `_index.md`（卷级）→ 分册/分区 `_index.md`（册级）。**新文档落位即同步登记两级索引**（实时同步义务，见 F2 映射表）；F4 双向核对机器兜底。agent 查询路径 O(1)：INDEX → 卷 → 文档/分册 → 条目。

**命名规范**：kebab-case 语义命名（命名即寻址，agent 可按约定预测路径）；**禁止日期堆叠进文件名**（日期属 frontmatter 与时间线；规划载体内开发者自留习惯不受此限）。

## 7.6 叙述层写作标准：文体学【v0.32，用户拍板：教科书式 + 门禁双保险】

**动机**：基线分类法定义了"架"（卷），但从未定义"书"（每篇藏书的文体与内部结构）——基准馆实证产出退化为"对账卡片/表格倾倒"（信息库形态），人类读者不可读。"叙述层讲理解"（§7 双层结构理念）自此转译为可操作标准与可执法门禁。

**三类文体（术语见 §4"文体"）**：

| 文体 | 定位 | 内部结构规范 |
| --- | --- | --- |
| `narrative` 叙述书 | 讲理解，给人读 | **导读**（H1 后首个非空段落，无 H2，兼作人与 agent 的摘要锚点）+ `## 为什么`（动机/设计决策/被否备选）+ `## 是什么`（概念/结构/职责）+ `## 怎么运转`（行为/流程/边界）——三段硬性；`## 怎么验收` / `## 参考`（交叉引用）可选；允许增补自定义段，不可缺标准段 |
| `ledger` 登记簿册 | 供查询，给机器 | 册导读段（首段：本册范围/图例/状态说明）+ 五要素条目（Q26 框架不变）；表格倾倒在此合法 |
| `index` 索引页 | 导航 | INDEX/_index/README 既有规范不变 |

**卷默认映射**（识别优先级：frontmatter `type` 字段 > 卷默认；存量文档零迁移）：

| 卷 | 默认文体 | 说明 |
| --- | --- | --- |
| 00-overview | index（豁免结构检查） | feature-map/progress 为账本、project/glossary 短叙述——混合区 |
| 10-architecture / 20-modules / 30-features / 40-guides / 50-testing / 70-deploy / 80-design | narrative | 80-design 的 routes/ui-assets 册以 `type: ledger` 覆盖 |
| 60-config / 90-reference | ledger | 叙述型反例以 `type: narrative` 覆盖 |
| 95-lessons | 豁免结构检查 | 既有"现象/根因/解决/规避"规范不重复造轮子，仅查注记污染 |
| 50-testing/benchmark/ 分区 | 豁免 | 基准实验档案区——过程材料（答卷/差异/回灌建议）的合法居所，同 99-archive 语义 |
| 99-archive、根 README/INDEX | 豁免 | 档案卷与导航页不参与 |

**门禁四检查**（机器确定性维度，落地于 F4；分级同 F13）：

| # | 检查 | 规则 | 级别 |
| --- | --- | --- | --- |
| 1 | 结构完备性 | narrative 缺导读或三段（H2 固定措辞匹配） | 违规（strict 阻断） |
| 2 | 卡片化 | narrative 正文有效行 <10 **且** 有效字符 <400（双阈值——抓内容稀薄而非行数；Markdown 段落一行属正常形态） | 违规（strict 阻断） |
| 3 | 注记污染 | 正文含四类过程短语类工作痕迹（词面清单见 doclib-build skill「写作方法论」与 `src/core/docquality.ts` POLLUTION_PATTERN；规范文档以抽象指代防自指误报）——实验编号行内注记（补丁式编号引用）由 audit 语义抽查兜底 | 违规（strict 阻断，全文体生效） |
| 4 | 倾倒 | 表格/列表行占正文比例 >70% | 警告（永不阻断） |

**配比与粒度原则**（skill 方法论层）：叙述与表格配比——表格承载枚举事实，叙述承载动机与机制；一篇书回答一个主题，正文 <10 行且 <400 字符即卡片化回炉，>300 行考虑按主题拆分（分册阈值 30 篇不变）。**draft 降级**：`status: draft`（init 骨架/占位态）文档的结构与卡片违规降级为警告（不计 strict 门禁）——draft 不豁免（警告仍可见），注记污染不降级；写完升级 status 即回归严格态。

**存量策略**：不强制追溯、不新增豁免机制——靠 soft/strict 分级报告缓冲，整改由用户显式触发（update 增量合规或专项清理）。

**落地分布**：理念本节；写作方法论进 doclib-build skill；update 保持文体合规；rebuild 回灌沉淀规则（F3）；门禁 src/core/docquality.ts（verify/check 集成）；骨架各卷 `_index.md` 内嵌本卷文体模板（init 落位即见）；语义层裁决归 doclib-audit 抽查。

### F12 数据库迁移治理（P0）【已确认 v0.14，Q18：混合账本制 + forward-only】

**问题**：长期开发中 agent 对迁移治理容易失控——随手改已执行脚本、重复编号、迁移与文档脱节。

**混合账本制**：

- **实体在代码区** `migrations/`（不进图书馆）：命名 `NNN_YYYYMMDD_<slug>.sql`——全局递增序号是执行顺序的唯一权威（同日多迁移不冲突），日期满足人读审计，slug 表达语义
- **图书馆持有治理账本** `10-architecture/migrations.md`：全局唯一取号出处 + 登记表（编号/日期/文件/目的/关联 .plan·feature-map/状态/数据风险）

**纪律（写入骨架模板与引导）**：

1. 取号：新迁移必须从账本取下一个序号，账本是唯一编号事实源
2. 不可变：applied 脚本禁止修改/删除（漂移检测兜底抓违改）；错误用新增补偿迁移修复
3. forward-only：默认不写 down 脚本；"回滚" = 补偿迁移，账本记 rolled-back
4. 登记即完成：迁移文件落盘与账本登记是同一步（实时同步原则）
5. 数据风险：破坏性变更（删列/改类型/锁表等）必须显式标注并写缓解措施

**存量收编【v0.17】**：对已存在乱象的 repo（历史迁移未登记、编号重复/断号、命名不一），首次建馆时做一次性盘点登记——账本**如实登记历史脚本**（旧号原样入账、标注旧制，**不重编历史**，符合 forward-only 与 applied 不可变）；新迁移一律从账本 max+1 取号；存量登记完成后，此后违规照常机器校验（乱象止于收编，不复积累）。

**序号权威原则【v0.17 泛化】**：任何序号型资产（数据库迁移、接口版本、卷编号等）以图书馆账本为唯一取号权威——"先取号、后落盘"，杜绝乱编号乱象在馆外滋生。

**集成点**：实时同步映射表加"数据库迁移/Schema 变更"行（AGENTS/CLAUDE/light/full/workflow 模板）；init 骨架自带账本卷；`10-architecture/data-model.md` 挂 Schema 演进指针。

| --- | --- | --- |

| 漏更 | covers 命中但全部未变 | 是 |
| 无归属 | 无 covers 命中 | 是 |

**归档闭环强验证【v0.36】**：用户实证「载体规划文档漏登记/进度账记一半靠自觉必漏」后拍板把可机器判定的归档失效面从 soft 提醒升级为 strict 不变量（`core/archival.ts` 三函数，ADR #20）——判定全部为**存在性/交叉引用**（零语义猜测零误报）：①载体未登记 ②进度账缺口 ③沉淀锚点缺失；经 pre-commit hook（F13 既有执法臂）自动阻断提交。**与 Q23 的分层调和**：mtime 型「待登记/待归档」提醒保持 soft（Q23 原拍板不变）；升级为 strict 的仅限存在性不变量子集。④教训账缺口【v0.37】——progress.md lesson-epoch 标记后条目强制 `教训:` 处置位、引用存在性核对（同日期+标题前缀），lessons 条目可加 `来源:` 行回溯；与 F9 边界干净（只查库内账本不解析载体）。治理健康分公式不变（四不变量不计入五分项）。

**孤儿文档收编【v0.17，第七分类；v0.20 升格为归位执法；v0.23 豁免清单定稿 Q20】**：`check` 扫描馆外知识型 Markdown（复用项目忽略规则），与 ack 账本比对后报告孤儿——孤儿即**归位宪法违反记录**（§7.5）：每份孤儿三态处置（同 F1 冷启动盘点）：**收编入馆（沿决策树定位唯一归宿）/ ack 豁免（理由留痕）/ 废弃清理**。默认豁免【Q20；多语言变体经 Q42 补】：根 `README.md`、`CHANGELOG.md`、`LICENSE`、`CONTRIBUTING.md`、**根级门面文件的多语言变体**（`README.<locale>.md` 等——locale 标签按 BCP-47 形状判定，模式识别而非逐项列举，Q42）、`.github/` 全目录、引导文件（已是文档账成员）、**已声明规划载体的内容**（F9 双轨边界）；docs/ 等历史目录**不整体豁免**（逐份判定）。孤儿清零即达成"馆外无文档"：图书馆是知识唯一事实源，全景可查。

**四态判定与三层防线【v0.29 新增，Q41 授权】**——原实现把"排除"压成一张平表（豁免即全丢），既误报又无处置。升格为：

- **四态判定**：①馆内 ②非文档资产（第三方/生成物/夹具——**不参与文档扫描**）③工具链豁免（工具链目录 + 任意层级引导文件 + 归档指针——**豁免但仍进代码账**，可漂移感知）④待归位孤儿（真·馆外知识文档——**唯一扣治理分、唯一计 strict 门禁**的态）
- **三层防线**：L1 扫描面（`DEFAULT_IGNORES` + `.doclibignore`）→ L2 判定面（工具链闭集 + `state.dirExempts`）→ L3 处置面（`doclib place`）
- **处置闭环**：`doclib place list`（待归位清单 + 决策树建议归宿）/ `collect`（收编入馆：移动 + frontmatter 补 covers + 两级索引登记）/ `archive`（入棺：移动 + 墓碑五要素 + 原路径留指针）/ `ack`（馆外合法登记）/ `restore`（归档账逆操作，不依赖 git）
- **入棺三道护栏**：写操作**默认干跑**（`--apply` 才落盘）+ `covers` 命中**硬拦截**（移动会砸掉增量更新锚点）+ **归档账可 restore**
- **闭集必然滞后**：内置闭集（27 项目录）+ `doclib ack --dir`（零代码扩展，不判孤儿但仍跟踪）+ `check` **疑似新工具目录软提示**（点目录 + 工具特征启发式，soft 不阻断）
- **漂移语义修正**：文件因新增忽略规则退出代码账 ≠ 真删除——`check` 按磁盘存在性区分二者，避免用户扩一次忽略规则即触发假「无归属」违规
- **豁免语义边界**：`ack --dir` = 不判孤儿但仍进代码账；`.doclibignore` = 完全不进代码账（不 hash、不漂移检测）

**治理健康分【v0.17；v0.23 精细分制定稿 Q22】**：基于 check 全部分类的**确定性量化**（纯计算、无 AI、可复现）。**分项加权制**：

| 分项 | 计分 | 权重 |
| --- | --- | --- |
| 对账完整性 | 1 −（漏更+无归属）/漂移总数，无漂移记满分 | 40% |
| 迁移纪律 | 迁移违规每项扣减，无违规满分 | 20% |
| 归位卫生 | 孤儿每项扣减，孤儿清零满分 | 20% |
| 引导新鲜度 | 引导过期每项扣减 | 10% |
| 文档质量 | 链接失效/依赖失配每项扣减 | 10% |

- 总分 = 各分项加权求和 ×100，下限 0；**等级字母承载分级**：A ≥90 / B ≥75 / C ≥60 / D ≥40 / F <40（ANSI 颜色不作承诺，字母即分级语义）
- 展示：`check` 输出末行"治理: NN/100 (X)" + 分项明细；`status` 展示"治理: NN/100 (X)"一行——腐烂趋势在会话开始即暴露
- 定位：**"越用越顺心"的可感知载体**——分数上升即治理改善；亦是 §9 判活标准的机器读数；权重可由 F14 基准实验数据校准

**实体级对账进阶【v0.18；v0.22 补引擎指针】**：check 从文件级向实体级延伸（分期随登记簿族），扫描引擎见 F15——

- 机器确定性扫描高价值实体（路由定义、图标引用等模式化目标），产出"实体漂移候选"→ agent 确认后对账（机器出候选、agent 裁决）
- 状态矛盾检测：代码已删而登记簿条目 `active` → 漏更；条目 `deprecated`/`removed` 而代码仍引用 → 可疑引用警告（顺带发现"该死没死"的资产）
- 登记簿 covers 命中率与实体抽查通过率纳入治理健康分读数（权重随 Q22 定稿）

**文档质量检测【v0.21】**：check 的确定性扩展，管"文档内部资产"的腐烂——

- **链接与路径引用存在性**：馆内文档间 Markdown 链接、指向代码路径的引用（covers 同源语义）做存在性校验——失效即报告（盲区 #13 链接腐烂）
- **依赖版本轻量对账**：60-config 登记的依赖版本/升级记录 vs manifest（package.json 等）实际版本，失配即提醒（盲区 #16）
- **边界**：只做存在性与一致性校验，不做内容语义判断——示例正确性/截图时效性归 audit 抽查与 F14 复原实验

**入馆写协调【v0.21 立项；v0.23 升级机器机制 Q36：乐观锁 revision 一步到位】**：多 agent 会话并发写馆的防护（盲区 #32）——

- **乐观锁 revision 机制**：state 增 `revision` 字段（每次 snapshot 递增）——agent 入馆写前记录当前 revision，写后跑 `doclib check` 比对；revision 已变 = 期间他人 snapshot 过 = 馆状态已被推进，**必须重新对账再继续**；check/plan/snapshot 均输出 revision 供比对
- 纯确定性、无锁文件、无写队列：不阻塞任何会话，只让"静默覆盖"不可能发生——后写者必然发现前写者
- 引导纪律（保留）：同一时间约定单会话执行"入馆写"；入馆写前先跑 `doclib check`
- 形态裁决记录：写队列/文件锁被否（复杂度高、阻塞型，与"可选增强优雅降级"哲学不符；乐观锁已使覆盖可检测）

**组成**：`doclib check [--strict]`（strict 违规退出码 1）；`doclib ack <path>`（once 绑定基线 snapshot 自动清除 / standing 长期 / --remove）；`doclib hook install [--strict] / remove / --ci github`（pre-commit 钩子带标记防覆盖，CI 模板）；旧基线无文档账自动降级并提示重建。**【已实现 v0.24：孤儿检测 + 治理健康分 + 乐观锁 revision 全部落地（src/core/orphan.ts / healthScore / state.revision），规格见 30-features/check.md】**

### F14 复原基准测试体系（P0）【v0.19 立项；操作指南 doclib/40-guides/benchmark.md】

**动机**：图书馆完备度无法自证——内容再全面也难以证明"特别全"，且图书馆内容本身需要被验证。方案【用户拍板】：给多个现有开源项目做图书馆，通过图书馆从零复原开发这些项目，对比原仓库与复原仓库的差异——差异即图书馆优劣之处，对症下药完善后回归尝试；基线、架构、方法论由此得到快速验证。**目的铁律【v0.28】：复原对比的对象是原仓库而非图书馆——"重建满足馆"只是自洽（循环论证）；馆的每一处遗漏都会变成重建与原仓库的实质差距，差距分析才是缺陷显影器。三阶段模型【v0.28】：P1 信息零遗漏（面穷举对账 Δ=0，CLI verify 守卫）→ P2 质量保证（行为双跑一致 100%+门禁全绿）→ P3 升华超越（复原产物修复原仓库 bug、做出提升，升华清单入档案）——三阶段串行，驱动 skills 与 CLI 分阶段升级。**

**基准库准入标准**：

- 体量：小中型（单 agent 数日可复原），宁选 CLI 工具/小型库/小型应用，不选框架级巨物
- 多样性：覆盖不同领域（后端服务/CLI/前端应用/数据处理），暴露不同卷的盲区（如 80-design 只有前端项目能测）
- 生态：宽松协议（MIT 等）、活跃维护、入口清晰
- 大项目允许**切片复原**（按功能部分复原），局部缺陷同样可暴露

**同题共答**：对比单位是**行为**而非字节——同一套验收标准在原仓库与复原仓库双跑，逐条对比结果；字节差异（代码风格/命名/quirk）是设计值，无意义。结构对齐度（模块职责/数据流/依赖）由 agent 评审辅助。

**双跑答卷规范【v0.27】**：验收标准必须可双跑——每条附可复现命令与期望结果（禁止"正常工作"类模糊表述），答卷按统一格式记录（`条目号 | 输入/动作 | 期望 | 实测 | 一致? | 证据`）+ 答卷头部运行时声明（node/依赖版本、环境前置），原仓库卷与复原卷同构，diff 即同题共答结果、一致率即复原度得分（模板见 30-features `_index`，执行见 doclib-accept skill）。

**缺陷四分类**（每个差异发现须分类，决定行动）：

1. 内容缺陷：该项目图书馆漏写某功能 → 项目级补账（回灌流程，Q6）
2. 结构缺陷：某类知识在 12 卷/登记簿 schema 装不下 → 产品级基线/PRD 演进——**多项目共性结构缺陷是基线演进的实证依据**（裁决 Q15/Q25/Q26）
3. 表述缺陷：写了但复原者读出歧义 → skill 方法论改进
4. 验收缺陷：验收标准不可执行/结果不可比 → 30-features 模板改进

**复原档案**：每基准项目一份档案（基线版本号、REBUILD-LOG、差异清单、缺陷分类账、修复记录）；图书馆结构版本变更后**必跑回归**，内容更新抽查跑——图书馆的测试套件，复原度得分的数据来源。

**污染防护**：建馆与复原必须**信息隔离**（F3）且使用**不同会话/实例**（理想为不同模型）——同 agent 先建馆再复原会带先验记忆，复原过顺则校准失真；REBUILD-LOG 记录复原者身份以审计隔离有效性。

**MVP 节奏**：先 1–2 个项目跑通全闭环（建馆 → 隔离复原 → 双跑对比 → 缺陷分类 → 回灌/改基线 → 回归重跑），验证方法论本身；再扩基准库至 3–5 个领域样本驱动结构演进。**首个基准项目【Q31】：colinhacks/zod**（44.2k★ MIT，TS 编写 ~2 万行；功能清单=API 清单天然可枚举，验收标准即"输入→解析→输出"对，双跑最顺滑）。

### F15 扫描器与工具集成（P1）【v0.22 立项，Q28/Q40】

**动机**：大 repo 场景下 agent 无法也不应读取全部代码（token 限制）——引入代码分析工具作为图书馆的**加速器**：实体扫描、符号定位、影响面分析。gh 实测选型（2026-10-19）：

**分阶段集成**：

- **阶段 0（现在，零依赖）**：纯 agent 扫描——登记簿建账/对账候选由 agent grep 完成（F1/F13 既有语义）；**旗标字面量双向对账【v0.33】**：馆内 md 的旗标长名 token（统一口径，短名同义不进对账）vs covers 锚定代码文件引号包裹注册字面量，双向 Δ 候选（源有馆无=遗漏/馆有源无=虚构或过时）——语言无关纯确定性（argparse/click/clap/cobra/commander 皆字面量注册），verify 面穷举节报告，agent 裁决（三铁律）；动机实证：csvkit 试点审查 6 缺陷（2 遗漏+2 虚构+共享面漏+同源联动）全部由此对账面一次抓获（ADR #16）
- **阶段 1（短期，可选增强）**：ast-grep 集成——`doclib` 探测 PATH 可用性；可用则实体扫描走**内置规则集**（Q28：全主流语言一次到位——TS/JS、Python、Go、Rust、Java/Kotlin、C#、Ruby、PHP、C/C++），产出 JSON 候选表；不可用则**优雅降级**回 agent 扫描；外部 bin 调用，**不进 npm 依赖**（守住"运行时仅依赖 ignore"）
- **阶段 2（已落地 v0.30）**：codegraph 克隆集成——git subtree 克隆 vendor/codegraph（v1.6.2 MIT）+ CJS 岛编译 + `createRequire` 单点桥；**F16 `doclib graph` 命令族**（index/status/draft/explore）+ 草稿候选管道（`.doclib/drafts/` 四册，机器出候选 agent 裁决）+ `init --graph` + BUILD 任务书候选段；无 daemon（查询时 catch-up sync）；telemetry 物理隔离；`.codegraph/` 定位为可再生缓存（非产物），图书馆仍是唯一事实源；用户裁决否决 npm 依赖直调（API/telemetry/深度耦合主权）与"F14 实测后裁决"顺序——**Q40 三指标转为事后验证**（下轮基准实验埋点：建馆耗时/查询耗时/缺口发现率）

**三铁律**：

1. **馆为唯一事实源，工具输出永远只是候选**，agent 裁决（"机器只出候选不代写"的延伸）——codegraph 输出永不直接入馆
2. **确定性/语义性分层**：ast-grep（确定性）服务 check 执法；codegraph（语义索引）服务查询加速——不可互相替代
3. **可选增强 + 优雅降级**：工具缺失不阻塞任何核心流程

**服务对象**：F13 实体级对账（候选引擎）+ F2 移除规程（步 1 影响面预查 / 步 2 残留扫描增强）+ 大 repo 符号导航。

### F17 规划直通车（P0）【v0.40 立项，Q43–Q48】

- **17c 拆单器（图书馆 → .plan 实施工单）**：`doclib implement [--feature N] [--apply]`——无 feature 列 planned 候选清单；有则 **readiness 校验**（对应文档列有值 + AC 锚点可解析——馆内依据齐备才可开工，BMAD readiness gate 的 DocLib 映射）→ 干跑展示骨架 → `--apply` 落盘 `.plan/<日期>/<slug>.md`；骨架 frontmatter `type: plan-skeleton` / `feature: N` / `generated` / `anchors: [<规格路径#AC-x>...]`，目的/边界/引用锚点预填（馆内确定性字段），方案设计/实施清单留 `TODO(agent)` 契约位（graph draft 同款惯例）；agent 面新 skill `doclib-implement` 对话填实（施工顺序/方案/备选），实施清单每条引用 AC 锚点，**填实保留 frontmatter**（执法前提）。落点语义：任务书 = `.doclib/tasks/` 簿记工单，实施文档 = `.plan/` 载体规划材料——落点不同语义不同，分开不混（Q41 同源逻辑）。
- **17d 门禁三件套**（check 违规类 14→17；全部存在性/词面判定零语义猜测，ADR #20 同范式）：① **acceptance-anchor**——载体中 `type: plan-skeleton` 生成物的实施清单条目缺 AC 引用 token、或引用的 AC 在馆内不存在（**仅约束 CLI 生成物，用户自由格式 .plan 不受检**——F9 不解析载体格式的边界守住）② **assumption-residue**——馆内 narrative 正文含未清 ASSUMPTION 词面（`status: draft` 降级警告，docquality 同构）③ **implementation-anchor**——feature-map in-progress 行对应文档列空/"-"（与沉淀锚点缺失镜像对称）。

**设计推论**：

- **AC 编号规范【Q45】**：30-features 验收标准编号 `AC-1..N`——新增文档强制、存量不追溯（Q33 先例）；AC 锚点贯穿「对话规划/工具转化 → 拆单骨架 → 施工自检 → accept 验收 → F14 同题共答双跑」**五处消费**——验收标准写一次全生命周期共用
- **双入口一管道**：对话规划（17a）与工具转化（17b）殊途同归——馆内各卷 + feature-map planned 条目（带 AC 锚点）；此后共用拆单器（17c）→ doclib-dev 开发循环 → 门禁（17d）
- **既有机制红利**：implement 生成的 .plan 文档须登记回 feature-map，否则触发「载体未登记」违规——闭环自洽，零新执法范式

### F18 记忆快照与协作者画像反哺（P1）【v0.41 立项，Q49–Q53】

**定位**：消除新会话冷启动记忆丢失——近 10-30 天工作轨迹与协作者画像以双层快照常驻引导文件，新会话零动作即得；快照是蒸馏物不是事实源，每条附真实路径指针可回溯，软执法防「记忆编造」。

**双层快照（memory 保留区，位于 project 与 custom 之间）**：

- **近期工作记忆（≤25 行，窗口默认 30 天【Q52】）**：当前焦点（feature-map in-progress #N + .plan 载体路径 + 一句话进度）/ 近期完成（窗口内 implemented 一行一条：日期 + slug + 一句话 + progress 指针）/ 活跃注意（progress 条目中未闭合的观察项/遗留建议）
- **协作者画像（≤12 行，不设硬窗口）**：决策风格（拍板偏好、典型否决理由模式）/ 沟通偏好（语言、详略倾向、协议习惯）/ 工作流习惯（会话节奏、高频指令、验收口径倾向）——沉淀**协作风格**不写私人化评价【Q53】

**机制（与 guide-project 注入管线同构）**：

- **落位【Q49】**：簿记单源 `.doclib/guide-memory.md`（frontmatter 携 `work-as-of`/`user-as-of` ISO 日期 + `window` 默认 30；非法 fail-fast；正文空=未蒸馏空状态合法；正文含区域保留标记 → 注入面 fail-fast/观测面降级 ⚠/执法面 fail-fast 三面分层）
- **注入【Q50】**：`renderFullGuide` 二段注入（project 后注 memory）；`mergeGuide` 不改（memory 区随模板整体再生）；`managedRegionFresh` 扩 memory 比对（直改 → guide-stale → sync 修复）
- **新鲜度（soft，仅 status）**：`work-as-of` 落后 progress 最新条目日期 → 「⚠ 工作记忆滞后 → 刷新簿记后 sync」；`user-as-of` 同法「⚠ 画像可刷新」；**不进 check 违规、不进治理分**——服务新鲜度≠事实源失真（反哺过期 strict 的正当性在于馆与引导失配）
- **反幻觉执法（soft）**：快照正文路径 token 逐个存在性核对（复用 lesson-source `SOURCE_PATH_TOKEN_RE` 词面范式）→ `memory-pointer` notice，不进 strict/治理分
- **预算【Q51】**：memory 区 ≤40 行独立预算（managed 150/project 50 不变），status 预算报告增报
- **素材边界【Q53】**：v1 只用馆内/簿记已蒸馏层——progress.md 时间线（骨架）+ feature-map 状态（焦点）+ in-progress .plan 载体（细节，agent 读，CLI 不解析——F9 合规）+ .plan 拍板记录节（画像主素材，原话保留）+ 98-sessions 现有导出件（旁证）；OpenCode DB 回捞（285 会话/2.5 万消息级）留 v2 联动 #34 `doclib transcript`
- **蒸馏执行者**：agent（会话收尾，planstore 四动作→五动作 + doclib-dev 自检第 4 问扩义）；CLI 只做检测/注入/软执法——「机器出候选不代写」哲学
