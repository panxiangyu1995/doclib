## 2026-10-17 · 空值 frontmatter 与 block 列表的解析陷阱

- 现象：`covers:` 空值先解析为字符串 `""`，导致后续 `- item` 行无处追加，覆盖映射静默失效；`covers: []` 被当成字面量字符串 `"[]"`，全馆文档被误报"失效"
- 根因：自写 YAML 子集解析器对"空值（待定数组）"与"内联空数组"两种形态语义未区分
- 解决：空值 → 空数组（可追加）；`[...]` → 内联数组解析
- 规避：frontmatter 解析器改动必须同时带 block 列表 / 内联数组 / 空值三形态的用例

## 2026-10-17 · 忘记调用落盘函数，"成功输出"≠"真实写入"

- 现象：plan 命令打印"已生成任务书"，文件却不存在——构建内容与写盘被拆成两步后遗漏调用
- 根因：函数职责拆分后，调用方缺少"返回内容 → 必须落盘"的强约束
- 解决：补 writeTask 调用；冒烟验证必须包含"输出后立即读取文件"的断言习惯
- 规避：命令收尾输出路径时，同命令内验证文件存在再打印

## 2026-10-19 · 子命令风格的 CLI 参数必须显式映射

- 现象：冒烟中 `doclib hook remove` 没有执行移除，反而以默认参数重新安装了钩子（覆盖了 strict 版）
- 根因：`remove` 被解析为位置参数后丢弃，runHook 未收到 remove 信号，落入 install 分支
- 解决：cli 对 hook 的位置参数做子命令映射（args[1] === "remove" → remove: true）；ack 的路径参数同理显式取 args[1]
- 规避：凡设计为 `命令 子命令` 的 CLI 面，解析层必须把子命令映射进选项；冒烟用例要覆盖"用户会自然输入的调用形式"而非只测旗标形式

## 2026-10-19 · sync 消费构建产物，改模板后必须先 build

- 现象：编辑 assets/guides/light.md 后运行 `doclib sync`，输出"无变化"，新规则没有传播到引导文件
- 根因：sync 的 writeGuides 读取的是 dist/assets/（copy-assets 的产物），源模板改动不经过 build 不会进入 dist
- 解决：先 `npm run build` 再 sync；引导/模板变更的标准流程固化为"改 assets → build → sync"
- 规避：任何"源资产 → 构建产物 → 运行时消费"链路，变更入口处必须提示构建步骤（未来可在 sync 输出中检测 dist 资产早于 assets 源时给出提示）

## 2026-10-17 · 脚手架命令必须区分"模板资产"与"用户内容"

- 现象：阶段 1 执行到本仓库迁移时发现，`init --force 覆盖同名模板`会摧毁 doclib/ 中 9 个手写同名文件（feature-map/progress/lessons 等真实数据）
- 根因：模板写入策略只在"引导文件"层做了无戳保护，图书馆模板层仍是粗暴覆盖；规划阶段未推演"init 在已有真实图书馆的仓库重跑"场景
- 解决：用户裁决跳过本仓库迁移（27-31）；后续版本将 init 模板策略改为"永不覆盖已存在文件，--force 仅绕过目录存在门禁"（与引导文件策略同构）
- 规避：任何脚手架/生成器命令设计时，先列出"哪些路径会与用户数据重名"，逐一路径定保护策略；规划清单里凡是写"覆盖"二字的地方都要做数据丢失推演

## 2026-10-22 · 基准打分测错了对象——同题共答自洽 ≠ 复原合格
- 现象：umami 首轮以"重建满足馆内验收标准"计 96.4%，回归 100%——但对照原仓库发现 12 个端点未实现、39 个页面缺失、i18n 结构形态偏离、/recorder 端点馆内漏登记
- 根因：验收标准来自馆——**馆漏了它就测不到**（循环论证）；把"馆自洽"当成了"复原合格"
- 解决：目的铁律入 benchmark.md 顶部 + PRD F14（对比对象=原仓库）；实质差距对比成为每轮必做（API 面枚举 diff/页面 diff/资产形态 diff/语义抽查）
- 规避：同题共答只是辅助；主持方每轮必做"重建 ↔ 原仓库"实质差距清单并逐条归因（馆缺陷/取舍/偏差）

## 2026-10-22 · 豁免清单是闭集——必然滞后于生态，必须配零代码扩展路径
- 现象：孤儿检测的豁免清单只有 4 个目录前缀（`.github/ .claude/ .opencode/ .cursor/`），而 43 个主流仓库实测的 agent 工具目录有 26+ 项——`.agents/`（跨厂商一级目录）单目录就含 176 个 .md；43 仓样本实测：工具链类误报 2,052（工具目录 422 + 嵌套引导 68 + 第三方 889 + 变更集 631；均值 ≈48/仓，AI 工具仓最高 171）——夹具类 2,801 按 Q20 逐份判定**不**整体豁免（残余误报的主要来源之一）
- 根因：把"工具链目录"当成可穷举的静态清单来维护——但生态按周级速度新增（`.antigravity/` `.kilocode/` `.specstory/` `.crush/` 均为近一年出现）；闭集一旦写死，滞后是必然事件而非意外
- 解决：三层兜底——①内置闭集（27 项目录 + 任意层级引导文件 + 归档指针）②`doclib ack --dir <前缀>` 项目级零代码扩展 ③`check` 检出"疑似新工具目录"（点目录 + `SKILL.md`/`*.mdc`/引导文件/工具子目录特征）并 soft 提示——把"静默误报"降级为"主动提示"
- 规避：任何"白名单/豁免/忽略清单"设计，必须同时回答两个问题——①新条目出现时如何**不需改代码**就能生效 ②如何让用户知道该加（提示而非静默）。清单越大，越要把扩展路径做进工具而不是留给下个版本

## 2026-10-22 · "排除"一刀切会连跟踪语义一起丢掉——扫描面与判定面必须分层
- 现象：原实现只有"排除/不排除"一个维度——`.claude/`（工具链占位的技术资产，应被跟踪以感知漂移）与 `vendor/`（他人写的代码，不该进文档视野）落在同一张平表上；结果要么漏报要么过豁免，且用户扩一次忽略规则就把文件推出代码账、进而被判"真删除"→ 假「无归属」违规
- 根因：把三个正交问题压成一维——①哪些文件参与文档扫描（L1 扫描面）②哪些文件不判孤儿（L2 判定面）③孤儿怎么处置（L3 处置面）；"排除"一个动作同时想做三件事，必然丢语义
- 解决：升格为四态判定（馆内 / 非文档资产 / 工具链豁免 / 待归位孤儿）+ 三层防线（扫描面 / 判定面 / 处置面）；并区分豁免语义边界——`ack --dir`=不判孤儿但仍进代码账，`.doclibignore`=完全不进代码账；漂移计算按磁盘存在性区分"真删除"与"被新忽略"
- 规避：遇到"排除/忽略/白名单"类需求，先问三句——排除了还算不算被跟踪？排除了算不算违规？后续要重新纳入时数据还在吗？三句都答得出，设计才算闭环

## 2026-10-22 · 闭集的根治是模式识别，不是逐项列举

- 现象：新增 `README.en.md` 时 `EXEMPT_ROOT_FILES` 精确闭集不命中 → 同时触发「无归属」与「孤儿文档」两类违规，迫使用户逐仓 `ack` 登记兜底
- 根因：把「生态惯例」编码成「文件清单」——惯例是可推导的**族**（基名 × locale × 目录层级），清单只能列举当下实例；与本卷 2026-10-22「豁免清单是闭集」条同源，但那一次只给了兜底（`ack --dir` 零代码扩展），没给根治
- 解决：`isRootFacadeFile` 改模式识别——基名 ∈ {README, CHANGELOG, CONTRIBUTING} 且 locale 标签符合 BCP-47 形状（`en`/`zh-CN`/`pt_BR`/`sr-Latn` 命中；`wip`/`2024`/`abc` 不命中），变体与基名在孤儿判定面同权；「无归属」面保持不变（不因语言宽严不一）
- 规避：设计任何「白名单/豁免/忽略」时先问一句——**这是集合还是族？族必须编码为模式**；若只能退而用闭集，必须同时给出零代码扩展路径（本次即以 `ack` 为过渡、模式为终局）

## 2026-10-26 · POSIX sh 双引号内 $变量 紧邻全角字符会静默吞掉展开——生成 shell 脚本必须用花括号
- 现象：真实仓库验收 CLI 缺失指引时，stderr 输出 `CLI 不存在（` 后路径消失、"）"残缺（hexdump 实证 `/nonexistent/path/cli.js` 的 24 个 ASCII 字节全部丢失，全角右括号仅剩尾部两字节）；macOS `/bin/sh` 与 bash 双双复现
- 根因：`"$CLI）"` 中变量名解析在多字节字符首字节处的行为——`$CLI` 紧邻 `）`（U+FF09）时 sh/bash 把该 UTF-8 序列卷入变量名匹配，`CLI）` 不存在 → 整段展开为空；对照实验：变量后加 ASCII 空格即正常，`${CLI}` 花括号形式根治（`}` 是明确的变量名终止符）
- 解决：hook.ts 脚本模板三处 `$CLI` 统一改 `${CLI}`；测试加回归守卫——断言钩子脚本中不存在「CJK/全角字符紧邻 $」模式（正则 `[CJK]$`）
- 规避：任何**生成 shell 脚本**的场景（钩子/CI 模板/安装器），双引号内的变量引用一律写 `${VAR}` 花括号形式，不依赖"后一个字符是 ASCII"的侥幸；涉及多字节文案（中文标点/emoji）的 shell 模板，验收必须做到字节级（hexdump），肉眼看终端输出会被编码显示掩盖
- 来源：progress 2026-10-26 hook 门禁真实仓库严格验收（P8）；.plan/2026-10-26/hook-hardening.md

## 2026-10-26 · init 集成可选增强必须全接降级——部分 catch 等于没 catch

- 现象：REVIEW 实证 init/sync 门禁集成块首版仅按 `instanceof DoclibError` 过滤 catch，损坏 .git 指针/底层 fs 错误直接炸 init，违反「init 绝不因门禁失败」拍板语义
- 根因：把「捕获业务错误」当成「捕获一切异常」——可选增强的失败面包含任意运行时错误，类型过滤只接得住自己抛的那部分
- 解决：集成块 catch 全接、降级为「跳过（原因）」行（与 graph 初始化同构的全接先例）；首版限定被回归用例抓出修复不完整后补全
- 规避：可选增强集成块的 catch 必须无类型过滤；评审「部分 catch」按「没 catch」对待
- 来源：progress 2026-10-26 hook REVIEW 轮（D-01）；.plan/2026-10-26/init-auto-hook.md

## 2026-10-26 · 幂等覆盖写不保文件模式——writeFile 的 mode 仅新建生效

- 现象：钩子幂等重装后既有的 0644 仍是 0644，git 静默忽略无执行位的钩子，门禁静默失效（探针实证）
- 根因：node fs.writeFile 的 mode 参数只在文件新建时生效，对既有文件不重新 chmod——「幂等覆盖」想当然假设了 mode 会重设
- 解决：writeFile 后无条件 chmod 0o755
- 规避：凡「覆盖式安装」语义的写入，权限/模式必须显式重设，并为重装路径补单测（新建路径测试覆盖不了它）
- 来源：progress 2026-10-26 hook REVIEW 轮（D-02）

## 2026-10-23 · 行数是稀薄度的劣质代理——Markdown 段落是一行

- 现象：card 门禁 800 字符阈值误伤合格精炼文档（实测合格区 440-797 字符），真实抱怨案例约 200 字符
- 根因：Markdown 源文件一个段落就是一行，行数不反映内容量；源码行数思维平移到标记语言，把「长段落」与「充实」混同
- 解决：行数+字符数双阈值（<10 行且 <800 字符，后校正为 <400），语义不变抓稀薄、长段落不误报
- 规避：对标记语言设计量度，先问「该语言里什么才是内容的代理」——不能直接搬源码度量
- 来源：progress 2026-10-23 文体门禁三项发现回流①；.plan/2026-10-23/genre-system.md

## 2026-10-23 · 规范文档描述禁令时不落能力词面值——自指违规

- 现象：旗标面对账把 PRD/decisions 中描述对账能力的字面值当作馆内旗标 token 候选，同类自指误报第三次发生
- 根因：规范文档必然要「谈论」它规范的能力——词面值一旦落进叙述文，对账面的 token 扫描就会命中自己
- 解决：规范文档用抽象措辞描述能力，词面清单只在 skill 与代码常量单点维护，grep 清零
- 规避：写规范涉及字面值禁令时措辞即抽象化；设计对账工具时把「规范文档自指」列为已知误报源
- 来源：progress 2026-10-23 旗标面对账落地④（第三次自指复盘）

## 2026-10-26 · 验证 CLI 副作用必须断言状态落盘值——二次调用有覆盖语义

- 现象：临时仓第二次 `init` 未加 `--force`，报错被输出重定向吞掉，规划载体声明未更新，提醒未触发——差点误判「声明后提醒失灵」
- 根因：CLI 二次调用有覆盖/拒绝语义（图书馆已存在需 `--force`）；验证只看命令退出与输出，没断言状态文件实际落盘值
- 解决：重跑补 `--force` 并直读 .doclib/state.json 断言 planning 实际值
- 规避：验证副作用类功能，断言对象是落盘状态而非命令输出；探针脚本重定向 stderr 必丢单一信息源
- 来源：.plan/2026-10-26/archival-loop-enforcement.md §八

## 2026-10-26 · 显式测试列表的代价——新增测试文件漏登记即静默退出执法门

- 现象：#35 新建的 `src/core/archival.test.ts` 未登记进 package.json test script（ADR #5 显式列出而非 glob），当时报告的「291/291 全绿」实际不包含这 8 个用例——测试静默不进 CI/pre-commit 执法门
- 根因：显式列表防 glob 误吞（Node 24 目录解析缺陷），但代价是「新增文件」是清单外动作——建文件与登记两步分离，漏第二步无任何报警（构建绿、旧用例绿、新用例根本没跑）
- 解决：test script 补登记 dist/core/archival.test.js；并以「dist 内 *.test.js 全集 vs test script 清单」diff 自查（本轮实证仅此一处遗漏）
- 规避：新增 *.test.ts 的完成定义（DoD）必须含「test script 登记 + 清单 diff 自查」；工具化候选：check 增「测试文件未登记」分类（后续立项）
- 来源：.plan/2026-10-26/lesson-gap-enforcement.md 执行期发现
## 2026-10-26 · 自由文本注入保留标记区域必须 fail-fast 校验——注入产物即契约面

- 现象：#32 REVIEW 实锤——蒸馏正文若含区域保留标记字符串（doclib:managed/project/custom begin/end），注入会破坏引导文件三区契约与 custom 保留语义，且观测面先于注入面暴露
- 根因：把注入目标当「纯文本容器」，没把保留标记当注入输入的非法值——渲染物的结构完整性依赖输入校验，而非渲染后补救
- 解决：注入面（init/sync）fail-fast 报 DoclibError 拒绝注入；观测面（status/verify）降级 ⚠ 提示；执法面（check）fail-fast——三层同一判据
- 规避：凡「自由文本注入结构化区域」的渲染器，保留标记必须列为输入校验项（fail-fast 优先于静默剥离）
- 来源：progress 2026-10-26 #32 REVIEW 轮 D-1；.plan/2026-10-26/guide-feed.md

## 2026-10-26 · 验收脚本链式调用须显式处理命令返回码——grep -c 零匹配静默断链

- 现象：真实仓库验收探针中 `base=$(… | grep -c …)` 零匹配返回码 1，`&&` 链后续追加未执行，且 strict exit=1（基线预存违规）被误读为注入效果——探针结论差点失真
- 根因：`&&` 链假定每环成功，但 `grep -c` 语义是「零匹配=失败」；命令替换的退出码会被赋值语句继承
- 解决：链式探针改 `;` 显式分步，或对计数类命令 `|| true` 归零；结论以落盘文件 diff 为准（同「CLI 副作用必须断言状态落盘值」条同源）
- 规避：验收脚本里凡返回码有语义的命令（grep/test/find）进 `&&` 链前先想「零命中时该不该断」
- 来源：doclib/50-testing/acceptance-lesson-gap-v0.6.2.md（F-2）

- 根因：文件系统 mtime 精度跨环境不一致（本地 APFS ns、CI overlayfs 整秒），而测试用「写完文件 → 断言它比刚创建的基线新」来构造前提；该前提与时间戳精度耦合，且**本地与 CI 的表现方向相反**（本地靠运气、CI 必红）——这类断言的「绿」是伪信号
- 解决：测试内显式 `fs.utimes` 把文件 mtime 设定为基线之后 5s，断言与文件系统精度彻底解耦；产品行为未改（软提示漏报仅在「文档与快照同秒创建」时发生，真实使用近乎不可能）；引导开发宪法「测试与验收铁律」同步增补该纪律
- 规避：凡断言涉及**跨对象时间先后**（mtime vs 快照时刻、文件 A vs 文件 B），一律显式设定时间戳（`fs.utimes` 或注入固定时钟），不得依赖「操作天然按序发生」；CI 红、本地绿时，先查**精度/时区/排序/并发**四类环境差异，再查逻辑；「本地靠 2ms 运气绿」是可识别的坏味道

## 2026-10-27 · frontmatter 扁平解析器不支持嵌套 YAML——schema 设计前先核解析器契约

- 现象：F19 test-chain 最初按嵌套 YAML 设计（`test-chain:` 下 `fast:`/`full:` 子键），实现时发现 `parseFrontmatter` 是扁平键值解析器——缩进键 `  fast:` 不匹配键正则被静默忽略，其下的列表项全部并进父键 `test-chain`，fast/full 两档合并成一个列表，分档语义静默丢失
- 根因：`core/frontmatter.ts` 的解析契约是「顶层键 + 紧随列表项」，靠 `currentKey` 游标把 `- item` 挂到最近顶层键；嵌套结构里缩进子键既不是键也不是列表项，被静默跳过——解析器**不报错但不语义**，是静默失真而非显式失败

- 规避：任何新增 frontmatter 字段的 schema 设计，先读 `parseFrontmatter` 的解析契约再定形状——多层数据用多扁平键编码（或走 JSON 簿记），不假设 YAML 嵌套可用；解析器静默忽略的输入要靠 fail-fast 探测兜底

## 2026-10-27 · 状态机判定要贴施工时序——开工即全未勾是常态，执法点选在「宣称完成」而非「进行中」

- 现象：skeleton-progress 批准稿判「in-progress/implemented 存在未勾选条目均 strict 违规」，执行推演发现 in-progress=开工（开工时实施清单全部未勾选）→ 开工瞬间 check --strict 即违规、施工全程恒红——为长程回路制造永久噪声，与回路自身的收口流程（勾选→翻 implemented→commit）时序冲突
- 根因：把 demo 的布尔 passes 直接映射到 doclib 四态时忽略了状态机的**施工语义**——in-progress 是合法的「进行中」态而非「宣称完成」态；执法点选错状态等价于把过程纪律当成了结果门禁
- 解决：违规只挂 implemented（宣称完成必须清单全勾——反伪造核心）；in-progress 未勾选降为 skeleton-open soft notice（进度可见不阻断）——经用户拍板确认
- 规避：给状态机加判定前，先枚举每个状态下的**合法现场**（开工时清单长什么样、收口时长什么样），执法点必须落在「该状态的现场不可能合法出现此形态」的状态上；拿不准时推演一次完整施工时序再定稿
- 来源：.plan/2026-10-27/long-horizon-harness.md 失败尝试与踩坑节

## 2026-10-27 · 注记污染门禁只认词形不认结构位——答卷空占位列可全身而过

- 现象：第三梯队建馆后自检发现 docmost 样本的 30-features 规格里，每条验收标准行末都拖着答卷占位列 `| 实测 | 一致? | 证据`（17 篇规格 251 条 AC、753 个空单元格）——但 `doclib check` 报**违规 0、治理 100/100（A 级）**、strict 通过
- 根因：注记污染检测按**词形**匹配（若干具体的过程痕迹字符串），而答卷占位列是一种**结构位**——列头是词、单元格是空的，没有任何污染词出现在被检测的正文 token 上。词形检测对「空表格骨架」是盲区
- 解决：定点剥离占位列（AC 语义零改动，只删行末三段空列）；形态本身登记为下一轮基线演进候选（与 ADR #27 并列——两件都是「现有门禁/卷结构装不下」类缺口）
- 规避：写「污染检测」时区分两个面——**词形面**（具体词）与**结构面**（空占位列/空表格骨架/待填答案的表头）；质量门禁自查时同时看两面；机器门禁绿 ≠ 内容干净，**建馆收尾必须人工扫一遍「空占位列」形态**

## 2026-10-27 · 规划期粗算统计不是事实源——建馆期必须逐类重算并显式留痕差异

- 现象：第三梯队建馆时，规划期登记的粗算统计与源码实证多处不符：excalidraw「~292 个 appState 字段」实为 98 个顶层字段、「15 套字体」实为 11 目录、「59 种语言」实为 57 语言包、「115 条 e2e 规范」在本仓根本不存在；syncthing「69 个 /rest 端点」实为 65 条路径 + 4 条非 /rest 顶层路由、「45 包含测试」实为 49；documenso「无 in-repo docs」被证伪（仓库有 11 篇根级 md + `apps/docs` 文档站 173 文件）
- 根因：规划期的统计来自**跨仓粗粒度采样**（rg 计数 / 上游页面数字 / 人工读数），是**候选**而非事实；且采样口径（顶层字段 vs 嵌套子字段、路径 vs 方法-路径对、语言包 vs 语言数）随样本而异，不同口径的数字不可直接继承
- 解决：各样本馆按源码**逐类重算**并在样本册显式留痕差异（写明「上游粗算 X，实证 Y，以源码为准」）；**口径差异本身也入册**（如 appState 嵌套子字段随父字段登记未独立编号）
- 规避：凡「数字入馆」必问三句——**谁数的（人或工具）/ 数的什么口径 / 能不能重数**；重数后与原值不符就**两边都写**（差异是信息，静默覆盖才是失真）；下游档案引用上游统计时一律标注来源与口径

## 2026-10-27 · sparse checkout 未补齐会让覆盖度与上游文档面双重失真

- 现象：第三梯队样本克隆沿用上游会话实测期的工作副本，其中 formbricks 的 `docs/`（826 文件）与 plausible 的 `extra/lib/`（117）、`tracker/`（96）等目录是 sparse checkout **未落工作树**——结果 formbricks 覆盖度被记成 85%（未覆盖部分其实是没下载的文档目录而非代码），plausible 的企业版树与 tracker 树只能靠 `git ls-files` / `git show` 读取而无模块书与行为规格，且 formbricks 的上游 252 篇 mdx 收编判据因文件不在盘而无法逐篇核
- 根因：sparse checkout 是**工作树形态**的省流手段，而建馆的三件事（覆盖度统计 / 上游文档收编 / 行为规格展开）都假定工作树完整；两者假设不一致
- 解决：建馆前 `git sparse-checkout disable`（或按需补齐目标目录）把工作树补全再开工；补不齐的目录必须在样本册「已知缺口」显式列出（不得只体现为「覆盖度 85%」）
- 规避：**克隆即定形态**——建馆用的克隆不许带 sparse / partial / filtered 标记；开工前先跑一遍「工作树完整性」自查（`git ls-files` 与实际落盘文件数对比），把「没下载」与「没覆盖」两类缺口分开记

## 2026-10-27 · 引导刷新必须排在基线固化之前——否则对账面把引导漂移算成漏更

- 现象：9 个样本馆收尾时先 `doclib snapshot` 后 `doclib sync`（刷新引导反哺区）——sync 改写了 AGENTS.md / CLAUDE.md，`doclib check` 随即把这两份文件判成「代码漂移」，对账分项归零、治理分从 100 掉到 **60（C 级）**、strict 门禁不通过；重跑 snapshot 后才归位
- 根因：`snapshot` 是**基线固化**，`sync` 是**对基线的写入**——顺序反了就把一次合法刷新记成「未同步的漂移」；对账分项的口径是「相对基线的未解释变更」，引导刷新恰好制造了这种变更
- 解决：收尾固定顺序 **`verify` → `sync` → `snapshot` → `check`**；改完文档若再次触达引导内容，重复 `sync` → `snapshot` → `check`
- 规避：凡是「会改工作区文件」的命令（sync / snapshot / place collect / implement --apply）都要问一句「它相对基线算不算漂移」，据此排出**「先改内容 → 再固化基线 → 最后执法」**的收尾序列；把收尾顺序写进 skill 的收尾清单，别靠记忆
- 来源：.plan/2026-10-27/benchmark-tier2.md 失败尝试与踩坑节

## 2026-10-27 · 上游文档充裕时的收编判据——「系统保证什么」入馆，「人该怎么做」不收编

- 现象：formbricks 是第三梯队唯一自带完整文档体系的样本（252 篇 docs mdx + ACCESSIBILITY.md + GLOSSARY.md），而研究期结论是「in-repo docs 数量与交互复杂度成反比」——文档充裕的样本面临另一类风险：把上游文档整段搬进馆造成重复与降格，馆反而变胖变钝
- 根因：文档收编缺判据时，默认动作是「搬」——但上游文档的**叙述对象不同**（有的写系统保证什么，有的写人该怎么做），后者对「从零复原」零信息量
- 解决：三段式判据落进 `40-guides/benchmark.md`「上游文档的收编判据」小节——**主判据**（描述系统保证什么 → 入馆；描述人该怎么做 → 不收编）+ **三条补充条款**（不重复：上游已说清的只引路径不搬段落 / 不降格：不弱化上游语义强度 / 切片一致：切片外能力即使有价值也不收编，否则验收范围与边界打架）；实测结果按四态判定入册（formbricks：入馆 114 / 非文档资产 572 / 工具链豁免 3 / 待归位 137），**上游 GLOSSARY.md 与 ACCESSIBILITY.md 转写为馆内术语表与无障碍册，不另起炉灶重写**
- 规避：收编上游文档前先定判据再逐份判定；**判据本身要写进馆内 workflow**（「每日新增上游文档时用同一把尺子」），否则判据随会话消失、下一批文档又按个人偏好收；判据与结果同处一册，不拆开
