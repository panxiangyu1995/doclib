## 1. 背景与问题

1. 一个项目的完整知识（功能、结构、架构、设计意图、边界行为）散落在代码与开发者脑中，新环境/新人/新 agent 无法凭代码快速获得全貌
2. 直接克隆代码不可取：要的是**从零重新开发**的能力——文档承载意图与设计，而非字节
3. 传统文档是一次性产物：代码持续演进，文档迅速腐烂，没有人维护
4. 新项目与半成品项目同样缺少系统化的规格与验收载体——开发意图只存在于聊天记录与开发者脑中，agent 无法据此持续、可验收地开发

## 2. 产品定位

**北极星原则【已确认，v0.10】**：图书馆必须是**活的、可用的、利于项目开发的**——绝不是死的文档。

- **活**：三层保活（实时层 / 流程层 / 兜底层）保证图书馆与代码互相映证、永远新鲜；快照链可追溯
- **可用**：agent 无需人工交代即可自助使用（引导文件 + skills）；能直接依据图书馆开发与验收；知识广而全
- **利于开发**：图书馆不是开发后的产物，而是**开发的输入**——每次开发从图书馆出发、以图书馆验收

> 运行准则：一切后续设计决策以此为准绳——凡是让图书馆变死的方案（一次性生成、无人消费、纯事后补账）一律否决。

**核心定位**：DocLib 是一套**系统化的项目规格与验收系统**——纯 Markdown 文档图书馆是项目的唯一事实源，agent 依据图书馆完成开发与验收。

**一句话**：把任意项目蒸馏成一座**可复原的文档图书馆**：有索引、有层次、覆盖全；任何 agent 或人只凭这套文档即可在别处**从零重建**该项目（≥90% 功能复原）；且文档随项目演进**持续保活**。

**复刻的意义【已确认】**：复刻存量项目不是最终目的，而是图书馆设计完备度的**校准标尺**——只有当图书馆能达到高保真复原，才证明其结构足以驱动任何开发。此后同一套架子用于：从零开发新项目、接手开发到一半的项目继续开发与迭代。即：**复刻是验证手段，文档驱动开发是最终目的**。

## 3. 目标用户与场景

| 用户 | 场景 |
| --- | --- |
| 项目维护者 | 为项目建立图书馆（蒸馏）；日常二次开发后同步文档（保活） |
| 复原者 | 人或 agent 只拿图书馆，在全新环境从零重建项目 |
| 通用 agent | Claude Code、opencode 等任意支持 skills 的 agent——**一等公民用户**，进入项目即能自助理解如何使用 skills/CLI、如何读取图书馆 |

## 4. 术语表

| 术语 | 含义 |
| --- | --- |
| 图书馆 | `doclib/` 目录：纯 Markdown 层级的文档集合，最终交付物 |
| 簿记 | `.doclib/` 目录：CLI 私有状态（快照链、任务书），不属于图书馆 |
| 任务书 | `.doclib/tasks/*.md`：CLI 生成、agent 消费的工单（BUILD / UPDATE / REBUILD） |
| 基线 | 某时刻代码状态快照（逐文件 hash），保活循环的对比基准 |
| 漂移 | 当前代码相对基线的差异（新增/修改/删除） |
| 锚点 | 文档 frontmatter 中的 `covers` 字段：文档 → 代码路径的映射，增量更新的关键 |
| 复原 | 只凭图书馆从零重新开发出 ≥90% 功能一致的项目；**明确区别于克隆** |
| 引导文件 | 项目内的 `CLAUDE.md` / `AGENTS.md`：让通用 agent 自助理解如何使用 DocLib 的说明文件（见 F5） |
| 规划文档 | 用户开发前写在 `.plan/<今日日期>/` 下的规划材料：目的与效果、问题点、研究结果、代码实际情况、设计方案、备选方案、实施清单等（见 F9） |

## 5. 目标与非目标

**目标**

1. 蒸馏：任意代码项目 → 完整文档图书馆（见 F1）
2. 复原：图书馆 → 从零重建项目，功能复原 ≥90%（见 F3）
3. 保活：代码任何变更后文档可增量跟进，无论落后一个还是十个版本、甚至从未建过（见 F2）
4. 双受众：人能轻易读懂，agent 能精确解析与执行
5. Agent 自助：任何通用 agent 进入项目即可理解 DocLib 的使用方式（见 F5）
6. 文档驱动开发：新项目从图书馆出发开发，半成品项目补建图书馆后继续开发与迭代（见 F8）
7. 一键进入：npx 安装到任意 repo，按目标 agent 适配安装 skills 与引导文件（见 F10）

**非目标**

1. **不是克隆**：不搬运源码（≤10 行示意片段除外），不追求字节级一致；缺失的 ~10% 是设计值（代码风格、内部小函数、历史 quirk 天然不被文档承载）
2. 不替代版本管理（git）：DocLib 管"代码 ↔ 文档"同步，不管代码版本历史
3. 不绑定特定 agent 产品：skills 为通用格式，CLI 为独立进程

## 6. 功能需求

### F1 蒸馏 build（P0）【已确认目标，细节部分为提案】

输入：任意完整项目。输出：文档图书馆。

- 覆盖内容：功能、特征、结构、架构、数据流、依赖、设计决策、边界行为等**所有相关内容**
- 图书馆结构：有索引、有层次、覆盖全（结构规格见 §7）
- 生成方式：agent（按 doclib-build skill 的方法论）撰写；CLI 负责项目清单采集（语言/框架/入口/结构树）并生成 BUILD 任务书
- 反克隆铁律（写入 skill）：文档只写行为、契约、设计意图、验收标准

### F2 保活 update（P0）【已确认目标，细节部分为提案】

触发：项目发生任何二次开发/新开发之后。

- 冷启动：图书馆不存在 → 走 F1 全量蒸馏
- 热更新：图书馆存在且落后 N 个版本 → CLI 计算"当前代码 vs 最新基线"的漂移，映射出受影响文档，生成 UPDATE 任务书；agent 按最小扰动原则增量更新
- 版本间距无关性：落后的 N 个版本在最近一次 snapshot 时被一次吸收，流程不因 N 变大而复杂化

**实时同步原则【已确认，v0.9】**：12 卷基线**一视同仁**——开发中凡有改动触及任一卷的知识（测试发现 bug 与解决办法 → 95-lessons；lint/配置变更 → 60-config；部署变更 → 70-deploy；UI 变更 → 80-design……），agent 须**实时更新入馆**，不等事后 diff。此规则必须写入 CLAUDE.md / AGENTS.md 约束 agent（见 F5）。

保活分三层：

1. **实时层（主）**：开发中即时更新，由引导文件中的实时同步规则约束 agent
2. **流程层**：F9 双锚点——`.plan/` 规划工作流内的登记与归档
3. **兜底层**：`diff` → `plan` → UPDATE 任务书，捕获一切遗漏的漂移，保证最终一致

### F3 复原 rebuild（P0）【已确认目标，细节部分为提案】

输入：图书馆（+ REBUILD 任务书）。输出：全新目录中从零开发的项目。

- 信息隔离：复原者只允许读图书馆，禁止访问源项目
- 施工顺序：按图书馆内复原路线图分阶段推进
- 验收【已确认：纯 agent 自检】：agent 逐条执行图书馆内功能规格的可执行验收标准（Given/When/Then），过程与结果留痕于 REBUILD-LOG.md；功能总清单全绿 = 复原完成（90% 达成）。用户可随时抽查，但不作为流程必需环节
- 歧义处理：文档明确→照做；沉默→按架构卷惯例实现并记录；矛盾→按"行为规格 > 结构描述 > 架构总览 > 愿景"优先级裁决并记录
- 复原产出须附差异清单（文档未覆盖而自行决策/被迫偏离的部分），反哺图书馆下一轮更新
- 产物形态【已确认 Q3 + Q6：自带校准副本 + 回灌建议双通道】：复原完成时将图书馆副本放入新项目；收尾时 agent 按差异清单把实践中证实的细节回写进副本（副本成为"经过实践校准的版本"，与复原产物真实一致）；差异清单同时另存为"回灌建议"文件，由用户带回源项目按 doclib-update 流程决定是否回灌源图书馆。复原者信息隔离不变——校准只基于复原过程自身的发现，不访问源项目

### F4 覆盖度与质量 verify（P1）【提案】

- 覆盖率报告：代码文件中有多大比例被 covers 覆盖（区分代码/非代码，按目录分组列出未覆盖项）
- 失效文档检测：covers 指向的代码已全部不存在
- 索引完整性：INDEX 收录与实际文档的双向核对
- 说明：未覆盖 ≠ 必须建文档，粒度由 agent 按 skill 判断（目录级 covers 合法）

### F5 Agent 引导注入（P0）【已确认；v0.6 修订：扩展源项目轻量引导】

**复原项目——完整引导**【已确认】：在复原产出的项目中生成并维护 `CLAUDE.md` 与 `AGENTS.md`，使 Claude 等通用 agent 进入项目即能自助明白：

1. 本项目 skills 的位置、加载方式与各自适用场景
2. CLI 命令速查与三条工作流（蒸馏/保活/复原）的触发时机
3. 图书馆阅读指南：阅读顺序、covers 锚点约定、术语表位置
4. 必要的、要注意的、细节的使用注意事项
5. **实时同步规则**【已确认，v0.9】：12 卷基线一视同仁，开发中凡有改动触及任一卷知识即实时更新入馆（bug 与解决办法、配置、部署、UI……无一例外）

**源项目——轻量工作流提醒**【已确认，v0.6 新增】：源项目可（用户选择开启）写入轻量 `CLAUDE.md`/`AGENTS.md` 片段，仅声明 DocLib 工作流规则（**实时同步规则**、F9 双锚点归档、保活循环触发时机），不包含完整引导内容。

生成方式【已确认：CLI 模板 + agent 补充】：

- CLI 提供引导文件模板（固定部分：命令速查、阅读顺序、covers 约定等与 skills/CLI 行为严格同步）
- agent 在复原收尾阶段落盘模板并补充项目定制部分（本项目实际适用的 skills、注意事项等）
- 更新时机【已确认 Q4：三重机制】：① 引导文件头部带版本戳（doclib 版本 + 图书馆结构版本），`status` / `verify` 自动检测过期并提醒重新生成；② 实时同步原则覆盖引导文件本身——工作流相关变更时即时更新；③ UPDATE / REBUILD 任务书收尾步骤固定包含"检查引导文件"

### F6 CLI 命令规格（v0.1 原型已实现，待 PRD 稳定后校准）【提案】

| 命令 | 职责 |
| --- | --- |
| `init` | 初始化图书馆骨架与簿记目录 |
| `plan` | 生成任务书：BUILD（无基线）/ UPDATE（有漂移）/ REBUILD（`--rebuild`） |
| `diff` | 漂移报告：变更路径 + 映射到的受影响文档 |
| `snapshot` | 记录当前代码为新基线（图书馆版本 +1） |
| `status` | 版本/基线/漂移概览 |
| `verify` | 覆盖度报告（F4） |

技术形态【已确认】：TypeScript + Node；职责切分为"skills 定知识、CLI 管状态"；运行时依赖最小化。

### F8 文档驱动开发（P0）【已确认方向（v0.3），细节待澄清】

图书馆不仅用于复原存量项目，更是**一切开发与迭代的规格与验收基准**——任何项目（全新/半成品/成熟）都可以通过系统化图书馆进行接下来的开发。

| 模式 | 起点 | 图书馆角色 |
| --- | --- | --- |
| distill（存量） | 已有完整代码 | 由代码蒸馏而来；复原能力校准其完备度（见 F1/F3） |
| bootstrap（新项目）【提案命名】 | 想法/需求，尚无代码【已确认输入：对话式挖掘】 | agent 通过对话挖掘需求，直接把图书馆填实（无需用户预写需求文档）；功能以 planned 状态入 feature-map；agent 按图书馆开发并逐条验收 |
| resume（半成品）【提案命名】 | 开发到一半的项目【已确认规划来源：用户为主 + agent 建议】 | 已有代码蒸馏为 implemented 条目；未来功能规划由用户提供为主、agent 分析后可给建议供筛选，整理为 planned 条目；此后按图书馆继续开发迭代 |

设计推论（提案）：

- feature-map 状态机：`planned / in-progress / implemented / retired`——功能从规划到落地的全生命周期在图书馆中可见；保活循环同步维护该状态（进度账设计见 F11）
- 验收体系一等公民：30-features 的验收标准既是复原验收基准，也是日常开发验收基准
- 三种模式共用同一图书馆结构、同一保活循环、同一任务书机制，仅任务书类型不同（BUILD / BOOTSTRAP / RESUME / UPDATE / REBUILD）

### F11 进度账与对账兜底（P0）【已确认，v0.11】

**问题**：图书馆完整 ≠ 知道进度走到哪——开发到一半时，agent/开发者不知道进度对应图书馆哪些内容；且开发者可能忘记走 `.plan/` 流程，兜底不能依赖"每次都记得"。

**进度账（双层）**【已确认 Q16】：

- **状态事实源**：`00-overview/feature-map.md` 的状态字段（planned / in-progress / implemented / retired）——每条功能的精确进度，全馆唯一事实源
- **时间线视图**：`00-overview/progress.md`——按时间记录每次开发：日期、关联 `.plan` 文档、完成的 feature-map 条目、状态变化、涉及卷；快速回答"开发完成了哪些"
- 纪律：状态只认 feature-map，时间线只叙述不另立状态，避免两本账打架；progress.md 每条记录引用 feature-map 条目与 `.plan` 路径

**三层兜底（全部不依赖 .plan 存在）**【已确认 Q17：三层全上】：

1. **规则兜底**：引导文件（F5）写死会话纪律——会话开始跑 `doclib status`（看漂移与待办）；会话结束前自检：改动是否归档、feature-map 状态是否推进、progress.md 是否补记
2. **对账兜底**：CLI 对账报告——对比"代码漂移"与"进度账"：漂移路径无任何 planned/in-progress 条目对应 → 报"未登记的开发"；implemented 条目的 covers 失效 → 报"进度与代码不符"；任何 doclib 命令均可携带该对账输出
3. **重建兜底（终极）**：`doclib reconcile` 命令——即使 `.plan/` 全部遗漏、进度账彻底失真，基于快照链 + covers 映射 + 漂移自动生成"疑似已完成开发清单"，agent 逐项确认后补录 feature-map 与 progress.md。**进度永不真正丢失：代码 hash 与 covers 映射本身就是底层账本**

后置（路线图）：git hook / CI 集成对账，漂移未同步时在提交或流水线阶段警告。

### F9 规划文档工作流集成（P0）【已确认，v0.6】

用户既有工作流【已确认】：每次开发新功能前，将规划内容保存为文档，放入 `.plan/<今日日期>/` 文件夹，内容包含：想达到的目的与效果、问题点、研究结果、代码实际情况、设计的方案、有无备选方案、具体的实施清单等。**DocLib 不提供规划文档模板**【已确认 Q11】，完全保留用户的规划习惯。

**双锚点机制**【已确认 Q9】：

| 锚点 | 触发 | agent 动作 |
| --- | --- | --- |
| 锚点一 · 登记规划 | 规划文档完成后 | 将规划登记进图书馆：feature-map 新增 planned 条目（或更新既有条目）；受影响的架构/模块文档可加规划标注 |
| 锚点二 · 归档成果 | 该规划的开发完成后 | 双轨沉淀【已确认 Q12】：① 过程材料留在 `.plan/` 不动；② 长期价值内容（决策、研究结果、备选方案理由）沉淀进图书馆（ADR/规格/参考卷）；③ 更新受影响的正式文档与 covers；④ feature-map 状态推进 planned → implemented |

**提醒载体**【已确认 Q10】：

- CLI 检测：扫描 `.plan/` 文档与基线快照的时间关系，在 `status` / `plan` 输出中给出"待登记 / 待归档"提醒（提案：`.plan/` 加入快照忽略，不进代码快照、不进图书馆）
- 源项目引导文件：按 F5 轻量片段声明工作流规则，使 agent 在日常开发中被规则约束

目的【已确认】：

1. 图书馆内容实时保持最新——保活在开发流程内闭环，而非仅靠事后 diff 补账
2. 再开发新内容时，供 agent 参看图书馆，并与代码实际相互映证

## 7. 文档图书馆结构【已定稿：12 卷基线分类法（v0.7 扩充 / v0.8 定稿，后续查漏补缺）】

设计原则【已确认】：图书馆之义在**广而全**——凡项目涉及的知识类别皆应入馆。下列为**基线分类法**：agent 按 skill 依项目实际增补卷（编号顺延，如安全、国际化、性能、合规…），宁多勿缺；反之不适用的卷可标记不适用并说明理由，不得静默省略。

```
doclib/
├── README.md               # 入口：怎么读、维护铁律
├── INDEX.md                # 总索引：全部文档 + 一句话摘要
├── 00-overview/            # 项目定位、术语表、功能总清单（状态事实源）、progress.md 进度时间线
├── 10-architecture/        # 架构总览、数据模型、数据流、依赖选型与理由、ADR
├── 20-modules/             # 每模块一卷：职责、边界、契约
├── 30-features/            # 每功能一份行为规格 + 可执行验收标准
├── 40-guides/              # 复原/开发路线图、编码约定、开发工作流
├── 50-testing/             # 测试方案、测试矩阵、测试设置、运行方式
├── 60-config/              # 工程设置全集：lint/format、构建、CI/CD、环境变量、配置项
├── 70-deploy/              # 部署：环境矩阵、发布流程、基础设施、运维与回滚
├── 80-design/              # UI/UX：design.md、设计系统、交互细节、资产说明
├── 90-reference/           # API/接口/协议精确参考
└── 95-lessons/             # 经验教训：bug 与解决办法、代码审查沉淀、踩坑记录
```

各卷要点：

- **50-testing**：测试方案（策略/分层/覆盖目标）、测试矩阵（功能 × 环境 × 输入组合）、测试设置（框架/fixture/测试数据）与运行方式；bug 修复后的回归用例回填此处
- **60-config**：一切设置的"是什么、为什么、怎么改"——lint/format 规则及理由、构建管线、CI/CD、环境变量全集（名称/用途/默认值/是否必填）
- **70-deploy**：部署形态、环境矩阵、发布流程、回滚预案、基础设施依赖
- **80-design**：UI/UX 设计文档（design.md）、设计系统（颜色/字体/间距/组件规范）、关键交互细节、视觉资产位置
- **95-lessons**：与 F9 双轨沉淀对接——bug 与解决办法、代码审查结论、踩坑与规避；只记可迁移的经验，不记流水账；测试发现 bug 后**实时入档**（实时同步原则，见 F2）
- **实时性**：各卷一视同仁——开发中凡触及任一卷知识的改动，实时更新入馆，不待事后 diff（见 F2 实时同步原则）
- **10-architecture/dependencies**：依赖选型升级为决策记录——选了什么、为什么、考虑过的替代品、升级与替换策略
- **完备性判定升级**（提案）：verify 除文件覆盖率外，新增"知识类别完备性检查"——对照基线分类法与增补清单，报告缺失/未判定的知识类别

- 纯 Markdown 层级【已确认】：目录编号即层次，INDEX 即索引，frontmatter（YAML）为 Markdown 生态惯例，承载 covers 等机器锚点

## 8. 状态模型【提案，已按 v0.1 落地】

- `.doclib/state.json`：图书馆版本号 + 快照链（每条含逐文件 hash 表，上限 20 条）
- 漂移计算：当前文件 hash vs 最新基线
- 映射规则：精确路径优先，其次目录前缀；新增无覆盖 → 需落文档；covers 全失效 → 失效文档

## 9. 成功指标【提案】

1. **功能验收法**【已确认判定方式：纯 agent 自检】：复原完成后，agent 逐条执行功能规格验收标准并留痕；功能总清单（feature-map）全部条目有实现且验收通过
2. **覆盖度**：verify 报告中代码文件覆盖率，未覆盖项均有 agent 判断记录（建卷/建章/忽略）
3. **终极抽查**：陌生 agent 只凭图书馆回答——部署方式？核心数据流？任一功能边界行为？错误处理策略？配置项全集？——答不上的部分视为图书馆缺陷
4. **类别完备性**（提案）：verify 的知识类别完备性检查通过——基线分类法各卷均"已覆盖"或"显式标记不适用"，无静默缺漏
5. **判活标准**（提案）：图书馆在开发流程中被实际消费——每次新开发从图书馆出发（规划引用既有文档）、以图书馆验收；生成后无人消费的图书馆视为失败
